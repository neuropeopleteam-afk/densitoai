# DensitoAI — инструкция для эксперта-тестировщика (1 страница)

**Что тестируем.** Сервис автоматически оценивает качество DXA-снимков (поясничный отдел
позвоночника, проксимальный отдел бедра) и отмечает нарушения: для позвоночника —
«Некорректная укладка», «Не выравнена ось позвоночника», «Присутствуют посторонние предметы»;
для бедра — «Некорректная укладка», «Некорректная область интереса». Сервис **не** ставит
диагноз и **не** меняет исходные файлы.

## Шаг 1. Подготовьте данные
Сложите DICOM-файлы (или zip-архив с ними, структура папок любая) в одну папку, например
`/home/expert/dxa_test`. Ничего переименовывать не нужно.

## Шаг 2. Запустите обработку (одна команда)
```bash
./build_and_run.sh run /home/expert/dxa_test ./outputs
```
(при первом запуске собирается образ — 5–10 минут; далее — секунды). Без Docker:
`python src/inference.py --input /home/expert/dxa_test --output outputs/results.csv --xlsx --debug-csv`.
Альтернатива — веб-форма: `./build_and_run.sh api`, затем в браузере `http://localhost:8000/docs`
→ `POST /api/analyze` → загрузить файлы → «Execute».

## Шаг 3. Откройте результат `outputs/results.xlsx` (или `results.csv`)
Одна строка = один снимок.

| Колонка | Как читать |
|---|---|
| `anatomical_region` | «Поясничный отдел позвоночника» / «Проксимальный отдел бедра» — проверьте, что область определена верно |
| `quality_class` | **1 — есть нарушение**, 0 — снимок качественный |
| `violation_type` | какие именно нарушения (через `;`); пусто — нарушений нет |
| `quality_prob` | уверенность в наличии нарушения, 0…1 (чем выше — тем вероятнее) |
| `processing_status` | `Success` — обработан; `Failure` — файл не удалось прочитать (см. Шаг 5) |
| `time_of_processing` | секунды на файл (ожидаемо < 0.5 с) |

## Шаг 4. Что именно проверить и как зафиксировать замечание
1. **Область** определена верно для каждого снимка.
2. **Нарушения**: сравните `violation_type` со своим заключением. Отдельно отметьте
   пропуски (нарушение есть, система не отметила) и ложные срабатывания.
3. **Спорные случаи**: откройте `outputs/results_debug.csv` — там измеренные величины:
   `feat_axis_angle_deg` (наклон оси позвоночника, °), `feat_metal_metal_area_mm2` (площадь
   плотных инородных объектов, мм²), `feat_edge_distance_mm` (расстояние ROI бедра до края
   кадра, мм; ТЗ требует ≥ 20 мм), `feat_shaft_angle_deg` (угол диафиза), а также
   `<критерий>_score` и `<критерий>_threshold` — насколько близко к порогу было решение.
4. Замечание фиксируйте так: `image_uid` (или имя файла) — ваш вердикт — вердикт системы —
   комментарий (что именно система не увидела / увидела лишнего).

## Шаг 5. Строки `Failure`
Это файлы, которые не удалось прочитать как DICOM-изображение (битый файл, нет пикселей,
пустой кадр). Причина — в `outputs/results.log` и в колонке `error` файла
`results_debug.csv`. Такие строки получают консервативные значения (`quality_class = 0`,
`quality_prob = 0.5`). Если файл открывается в вашем DICOM-просмотрщике, а система выдала
`Failure` — это дефект, сообщите с приложением файла.

## Что важно знать заранее (честно)
- Наиболее надёжно определяются **посторонние предметы** и **наклон оси** позвоночника.
- По критериям **«Некорректная укладка» позвоночника** и **«Некорректная область
  интереса» бедра** обучающих примеров было очень мало (4–10) — ожидайте ошибок; ваши
  замечания по ним особенно ценны.
- Система обучена на снимках одного аппарата (GE Lunar); на снимках другого разрешения
  результаты могут быть хуже — такие файлы помечены в `results_debug.csv` предупреждением
  `non-standard image`.
- Обработка каждого файла независима: один плохой файл не влияет на остальные.
