# Зона «не уверен»: кривая «покрытие → полнота» (OOF 2.5.0, 27.09.2026)

Аналитический документ. Правило сервиса, пороги, запасы (`config.yaml -> uncertainty`), модели и 9 колонок CSV этим документом **не меняются**; здесь только измерение того, что даёт текущее правило и что дали бы альтернативные ширины зоны. Решение о смене правила — отдельное, по этому отчёту.

Инструмент: `tools/uncertain_zone.py`; машиночитаемый результат — `docs/uncertain_zone.json`; графики — `docs/uncertain_zone/coverage_recall_{spine,hip,criteria}.svg`; тест — `tests/test_uncertain_zone.py`.

## 1. Что измеряется

Текущее правило (`src/inference.py`): критерий «не уверен», если |score − threshold| <= margin[критерий] (запасы из `config.yaml`, получены `tools/uncertainty_margins.py` под квоту 5 % на критерий); строка `needs_review = 1`, если не уверен хотя бы один критерий области; `risk_level = средний`.

Для каждой ширины полосы δ от 0.00 до 0.30 с шагом 0.01 инструмент строит зону «не уверен» и считает на OOF-предсказаниях стэкинга (`models/oof_stacked_<область>_<критерий>.csv`, те же строки и разбиение GroupKFold, что в `docs/METRICS_REPORT.md`):

- **доля строк в зоне** (1 − покрытие); зона = хотя бы один критерий области попал в полосу;
- **полнота, специфичность, F1 среди уверенных строк** (флаг строки = хотя бы один критерий сработал; разметка строки = хотя бы одно нарушение);
- **доля положительных, попавших в зону**, доля всех ошибок класса в зоне, число пропусков (положительная строка без флага) в зоне;
- **полнота с учётом зоны**: положительные, у которых есть флаг или которые попали в зону (врач смотрит зону), делённые на все положительные;
- то же для каждого критерия отдельно (флаг критерия против разметки критерия).

Две семьи правил: **полоса по скорам критериев** (единый δ для всех критериев области вместо пяти разных запасов) и, для сравнения, **полоса по quality_prob** (|quality_prob − 0.5| <= δ; quality_prob воспроизведён так же, как в сервисе: any-модель с весом 0.5, согласование с классом). Отдельно считается **текущая точка** — запасы по критериям ровно как в `config.yaml`.

Доверительные интервалы 95 % — кластерный бутстрап по исследованиям (500 повторов, зерно 0), интервалы процентильные. Для кандидатных точек дополнительно **парный** бутстрап разности «кандидат − текущее правило» на одних и тех же ресэмплах исследований: если его ДИ содержит 0, прирост считается неотличимым от шума.

Ограничение данных: положительных исследований по критериям 6–17 (`sp_pos` 6, `sp_axis` 10, `sp_art` 17, `hip_pos` 24, `hip_roi` 6), пропусков на OOF 11 (позвоночник, 6 исследований) и 44 (бедро). Интервалы широкие, все выводы ниже — предварительные.

В 2.5.0 изменился только критерий `sp_art` (признак предметов в зоне измерения, `docs/NESTED_GATE_REPORT.md`, часть 8): порог 0.602 → 0.624, запас 0.012048 → 0.006469 (`tools/uncertainty_margins.py`, та же квота 5 %). Поэтому ниже меняются числа позвоночника; числа бедра совпадают с 2.4.0. Прежняя версия документа (OOF 2.4.0) — в истории git.

## 4. Полоса по quality_prob (для сравнения, в сервисе не используется)

Согласование quality_prob с классом (`consistent_quality_prob`) оставляет разрыв вокруг 0.5: на OOF строки без флага имеют quality_prob <= 0.366 (позвоночник) и <= 0.424 (бедро), строки с флагом — >= 0.732 и >= 0.711. Поэтому полоса |quality_prob − 0.5| <= δ при δ < 0.20 почти пуста, а при δ = 0.20–0.25 состоит из строк, где **any-модель расходится с решением по критериям** (без флага, но any-вероятность высокая — либо с флагом, но any-вероятность низкая).

На бедре при δ = 0.20 зона из 32 строк (все без флага, quality_prob 0.30–0.42) содержит 17 из 44 пропусков — при случайном выборе 32 строк ожидалось бы 4.3; парная разность полноты среди уверенных против текущего правила +0.168 [+0.05; +0.32], ДИ не содержит 0. Оговорки: 17 пропусков принадлежат 6 исследованиям (из 17 исследований с пропусками), quality_prob бедра до согласования калиброван слабо (`docs/CALIBRATION.md`: ECE10 0.225), и такая зона односторонняя — она никогда не помечает строки с флагом, то есть не снижает ложные срабатывания.

На позвоночнике 2.5.0 при δ = 0.23 зона из 9 строк содержит 5 из 11 пропусков (при случайном выборе ожидалось бы 0.6); парная разность полноты среди уверенных +0.081 [+0.01; +0.19], нижняя граница близка к 0. В 2.4.0 аналогичная точка (δ = 0.22) была в пределах шума. Пропусков позвоночника всего 11 в 6 исследованиях, поэтому это наблюдение, а не основание менять правило.

## 5. Кандидатные точки и рекомендация

Формальное правило выбора в инструменте: среди δ с долей «не уверен» <= 20 % (ориентир нагрузки на просмотр) — максимум пропусков в зоне сверх ожидания при случайном выборе того же числа строк; при равенстве — меньшее δ. Парная разность — полнота среди уверенных, кандидат минус текущее правило.

Вывод для решения.

1. **Текущее правило (запасы по критериям под квоту 5 %) разумно и менять его по этим данным не нужно.** Единая полоса по скорам не даёт прироста полноты среди уверенных, отличимого от шума, ни в одной области; выигрыш только в полноте с учётом зоны, и он покупается строками в зону почти линейно (позвоночник +6 строк за +0.017, бедро +22 строки за +0.065). При этом текущее правило удерживает `sp_pos` и `hip_roi` до обрыва, где все их положительные уходят в зону.
2. **Кандидаты с приростом за пределами шума** — дополнительное условие «any-модель расходится с критериями» (эквивалент полосы по quality_prob): для бедра δ = 0.20 (+1 строка в зону на OOF, полнота среди уверенных 0.472 → 0.640, с учётом зоны 0.587 → 0.707, парный ДИ [+0.05; +0.32]); для позвоночника 2.5.0 δ = 0.23 (−14 строк в зоне, полнота среди уверенных 0.810 → 0.891, с учётом зоны 0.867 → 0.900, парный ДИ [+0.01; +0.19]). Против: пойманные пропуски сосредоточены в немногих исследованиях (бедро — 6, позвоночник — не более 6), quality_prob бедра до согласования слабо калиброван, правило несимметрично. Это **отдельная задача** (изменение `src/inference.py`, config, пересчёт чисел поставки, проверка по протоколу вложенной GroupKFold) — не для сборки 2.5.0; предварительно нужен пересчёт на большем числе положительных исследований.
3. Для позвоночника в целом данных мало: 11 пропусков в 6 исследованиях.

## 6. Что изменилось бы на выгрузке прогона 2.5.0 (499 строк)

Проекция единой полосы δ на скоры прогона 2.5.0 на 499 кадрах (`results_debug.csv`, колонки `<критерий>_margin`; прогон на коде 2.5.0, в git не входит). В файле `needs_review = 19` (3.8 %, все на бедре); правило, восстановленное из колонок `*_uncertain`, даёт ровно 19; запасы `config.yaml` на тех же скорах — тоже 19. На позвоночнике у боевых моделей (обучены на всех 166 строках) ни один скор не попал в запас. Текст `note` в JSON (про модель `sp_pos` 2.3.2) выводит инструмент для прежнего файла `regress_2_3_2_debug.csv`; к этому прогону он не относится. ## 7. Как воспроизвести

```bash
OMP_NUM_THREADS=1 python tools/uncertain_zone.py --regress <results_debug.csv прогона 2.5.0> --markdown
python tools/p25/uncertain_zone_md.py --write
python tests/test_uncertain_zone.py
```

Флаги: `--n-boot N` (по умолчанию 500), `--seed` (0), `--out DIR` (каталог для JSON и SVG вместо `docs/`), `--no-svg`, `--markdown` (таблицы в stdout). Время полного прогона на 2 vCPU — около 5 с. В JSON и SVG только агрегаты: нет идентификаторов исследований, путей и кадров.
