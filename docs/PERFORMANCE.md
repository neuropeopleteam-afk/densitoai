# Паспорт производительности DensitoAI 2.4.0

Секунды на снимок и память сервиса — что измерено, в каких условиях и как повторить. Все числа
ниже получены скриптом `tools/perf_passport.py` и лежат в `docs/perf_passport.json`; документ
сгенерирован из него. Числа поставки (метрики, пороги, модели, `config.yaml`, 9 колонок CSV) не менялись.

Что измеряется. `time_of_processing` — секунды на файл, которые сервис записывает в CSV сам
(`src/inference.py: process_file`): чтение DICOM → область → признаки контура A → эмбеддинги
контура B → модели → строка. В него не входят загрузка моделей и прогрев бэкбонов (один раз на
процесс) и запись CSV/XLSX (один раз на пакет). Стена пакета = холодный старт + сумма
`time_of_processing` + запись.

## 4. Сопоставление источников

Медиана `time_of_processing` на боевом сервере под чужой нагрузкой (1,84 с) и в локальном замере (0,07 с) различаются в 26 раз при одном и том же коде пути (2.3.2 и 2.4.0 различаются одним признаком `sp_pos` поверх уже посчитанного эмбеддинга, см. CHANGELOG). Вероятная причина — условия, а не код: занятые ядра сервера во время прогона и переподписка потоков (`inference.py` ставит `torch.set_num_threads(min(8, cpu_count))`; при лимите CPU контейнера ниже cpu_count потоки конкурируют за ядра).

Тихий сервер (раздел 2) подтверждает: тот же сервер без чужой нагрузки даёт медиану 0,54 с и p95 1,76 с — в 3,4 раза меньше, чем под нагрузкой, и всё ещё в 8 раз больше локального замера (старее процессор сервера, OMP_NUM_THREADS=2 в контейнере, nice 10). Медианы по четвертям тихого прогона ровные.

В документах корректно писать так: «на боевом сервере в тихих условиях — медиана 0,54 с на снимок, p95 1,76 с (499 файлов за 368 с одним процессом, сумма `time_of_processing` 357,5 с; позвоночник 0,82 с, бедро 0,40 с); под чужой нагрузкой — медиана 1,84 с, p95 6,11 с (выгрузка 2.3.2); локально (песочница 2 vCPU, параллельная нагрузка других задач, OMP_NUM_THREADS=2, nice 5, ориентировочно) — порядка 0,07 с». Одно число без условий не писать.

## 5. Как воспроизвести

```bash
# (а) распределение time_of_processing по CSV поставки (секунды)
python tools/perf_passport.py --csv dataset/regress_2_3_2.csv
# раздел 2: CSV регрессии на тихом сервере; ручные числа (стена, API, RSS, образ) — JSON-строкой или файлом
python tools/perf_passport.py --quiet-csv dataset/regress_2_4_0.csv \
    --quiet-extra '{"container_wall_s": 384, "docker_image_gb": 2.57}'   # прежние ручные числа сохраняются
# (б) локальный замер на 12 файлах (6 позвоночник + 6 бедро, разные исследования; 3 прохода), ~1–2 мин на 2 vCPU
OMP_NUM_THREADS=2 nice -n 5 python tools/perf_passport.py --measure 12 --data /path/Исследования \
    --label "своя машина: N vCPU, что ещё работало"
# в образе: docker run --rm -v /path/Исследования:/data:ro <образ> python tools/perf_passport.py --measure 12 --data /data
# тест: воспроизводимость (а) и проверка аргументов, без долгого замера
python tests/test_perf_passport.py
```

Выбор файлов детерминированный (исследования по алфавиту, первый файл нужной области, по одному на
исследование), поэтому два замера на разных машинах сравнивают одни и те же снимки. Числа режима (а)
воспроизводятся побайтово; числа режима (б) — с разбросом машины.

## 6. Что это не значит

- Числа зависят от машины, числа потоков, соседней нагрузки и версии библиотек; на другой машине они другие.
- Пропускная способность (снимков в час) не обещается: сервис обрабатывает файлы последовательно в одном
  процессе, а требование ТЗ — не более 3 минут на исследование — единственная граница, с которой сравниваются числа.
- Сравнений с внешними ориентирами и другими инструментами нет и не подразумевается.
- Локальный замер сделан на 12 файлах, а не на 499; это оценка порядка величины, а не распределение потока.
- Время API с бонусными выходами (визуализация, SR, SEG) снято один раз на одной партии (раздел 2); это порядок
  величины, а не распределение; подробнее о режиме API — `README.md`.
- Пиковый RSS измерен как `ru_maxrss` процесса Python; память контейнера в целом (с ОС и кэшами) больше.
