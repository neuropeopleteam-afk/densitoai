# Экзамен на подсказки (shortcut audit), 24.09.2026; пересчёт для 2.5.0 — 27.09.2026

Вопрос: может ли качество сервиса объясняться не изображением, а тем, что сопровождает файл, — метаданными DICOM, размером кадра, числом файлов в исследовании, порядком строк, UID. Модели и пороги поставки не менялись; числа пересчитаны на поставке 2.5.0, где изменился только критерий `sp_art` (признак предметов в зоне измерения, `docs/NESTED_GATE_REPORT.md`, часть 8). Контроли части A от модели не зависят и совпали с 2.4.0; изменились столбец «Сервис (OOF)» для позвоночника и `sp_art`, срезы по версии ПО и строка `sp_art` части B. Скрипт `tools/shortcut_audit.py`, числа — `docs/shortcut_audit.json`, признаки контролей для 499 файлов — `data/slices/shortcut_meta_499.csv`.

## Протокол

- Кадры организаторов: позвоночник 166 кадров / 99 исследований, бедро 329 / 78; метки и боевые OOF-оценки — те же, что в `docs/METRICS_REPORT.md` (ROC-AUC 0.846 / 0.760).
- Проверка: `StratifiedGroupKFold(5)`, группы «исследование + хэш пикселей» (клоны одного кадра не расходятся по фолдам; на этих данных группы совпали с исследованиями), 10 повторов разбиения.
- **Часть A, отрицательные контроли.** Логистическая регрессия (StandardScaler, `class_weight='balanced'`) только на признаках без изображения:
  C1 — метаданные (SoftwareVersions, SeriesNumber, InstanceNumber, наличие необязательных тегов, корень UID папки);
  C2 — экспозиция (TotalNumberOfExposures, ExposedArea, EntranceDoseInmGy);
  C3 — размер кадра (Rows, Columns);
  C4 — число файлов в исследовании и число кадров области;
  C5 — порядок строк (номер строки, номер файла);
  C6 — хэш UID исследования и SOPInstanceUID.
  Нулевая полоса — те же признаки при метках, переставленных между уникальными кадрами (50 перестановок); контроль «сработал», если средний AUC выше 95-го перцентиля полосы.
- **Часть B, перестановка меток для стека изображения** с входами поставки (признаки контура A и вариант предобработки из `config.yaml`, боевой источник эмбеддингов, PCA 32; среднее двух вероятностей вместо рангового стэкинга — упрощённая копия обучения, не метрика сервиса): B1 — реальные метки; B2 — метки переставлены между уникальными кадрами (20 раз); B3 — внутри исследования (20 раз).

- B2: при перемешанных метках AUC в среднем 0.42–0.52 — протокол CV утечку не пропускает. Реальные метки выше 95-го перцентиля по всем пяти критериям. Полоса широкая там, где мало позитивов: у `hip_roi` одна перестановка из 20 дала 0.94, у `sp_pos` максимум 0.77. На 10–16 позитивах один AUC ничего не доказывает, отсюда пометка «ненадёжно» в `models/metrics_summary.json`.
- B3, позвоночник: метка одна на исследование, перестановка ничего не меняет; совпадение B3 с B1 — проверка корректности.
- B3, `hip_roi`: 0.90 → 0.74 — модель различает кадры внутри исследования (длина скана у сторон разная).
- B3, `hip_pos`: 0.678 → 0.725, то есть внутри 11 исследований с разными метками сторон модель сторону не различает: сигнал укладки бедра в основном уровня визита (телосложение, общая манера укладки). Это согласуется с тем, что контекст другого бедра визита не дал устойчивого прироста при полной проверке (`docs/NESTED_GATE_REPORT.md`, часть 7; `docs/qa/JURY_QA.md`, 14.9), и с ограничением F1 `hip_pos` 0.432.

## Итог

- Качество сервиса не объясняется метаданными, размером кадра, числом файлов, порядком строк или UID: на бинарных задачах обеих областей ни один контроль не превысил нулевую полосу, а перемешанные метки дают AUC около 0.5.
- Две связи найдены и названы: версия ПО экспорта связана с долей артефактов позвоночника (модель её не использует, различение внутри версий сохраняется); длина скана определяет `hip_roi` — это суть критерия, а не подсказка.
- Сигнал `hip_pos` — уровня визита, сторону внутри визита модель различает плохо.
- Ограничения: одна организация и один аппарат, две версии ПО; контроли — линейные модели, нелинейную подсказку они могут не увидеть; у `sp_pos` и `hip_roi` 10 и 16 позитивов.
