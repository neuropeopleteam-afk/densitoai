# Проверка поставки DensitoAI 2.4.0 (инструкция для технической группы заказчика)

> **Назначение и ограничения.** Программа не является медицинским изделием и не предназначена
> для диагностики, профилактики, лечения или мониторинга заболеваний. Сервис оценивает
> техническое качество укладки и области интереса исследования и не формирует медицинское
> заключение. Решение по исследованию принимает врач. Область применения: денситометрия (DXA)
> поясничного отдела позвоночника и проксимального отдела бедра, оборудование GE Lunar Prodigy;
> вне этой области применения результат не определён. Источник формулировки —
> `config.yaml → intended_use`, та же строка отдаётся в `/api/health` и показана в веб-интерфейсе.

Проверка выполняется на машине с Docker (Linux x86-64, 2 CPU и 3 ГБ памяти достаточно), без доступа в интернет.
Пик памяти процесса обработки в наших замерах — около 0,6 ГБ; самопроверка на 15 фантомах занимает
около 15–20 с на 2 vCPU (в стенде разработки: 12 с при одном потоке).

Паспорт производительности (секунды на снимок, память, условия, как воспроизвести) — `docs/PERFORMANCE.md`; на боевом
сервере в тихих условиях медиана 0,54 с на снимок, p95 1,76 с (499 файлов за 368 с одним процессом), под чужой нагрузкой
медиана 1,84 с. В образе: `docker run --rm -v /path/Исследования:/data:ro <образ> python tools/perf_passport.py --measure 12 --data /data`
(12 файлов, около 1–2 мин на 2 vCPU; выход — `docs/perf_passport.json`, `docs/PERFORMANCE.md`); числа тихого сервера
подставляются из CSV регрессии (`--quiet-csv`, ручные числа — `--quiet-extra`). Тест `python tests/test_perf_passport.py` —
секунды, долгий замер не запускает.

## Пять команд

1. Проверить контрольные суммы и загрузить образ.

        cd dist && sha256sum -c SHA256SUMS && cd ..
        docker load -i dist/densitoai-2.4.0-image.tar.gz

2. Самопроверка образа без сети (фантомные DICOM внутри образа, два прогона, сравнение с эталоном, sha256 весов).

        mkdir -p outputs
        docker run --rm --network none --cpus=2 --memory=3g --user "$(id -u):$(id -g)" \
          -v "$PWD/outputs:/data/output" densitoai:2.4.0 verify
        # то же одной строкой: bash tools/offline_check.sh densitoai:2.4.0 ./outputs

   Код возврата 0 — все проверки пройдены; 1 — есть расхождение. Отчёт: `outputs/verify/verification_report.html`
   (таблица проверок зелёным/красным, карта доказательств «что вы теперь знаете» с привязкой к пунктам ТЗ, блок «что отчёт не доказывает»,
   версии пакетов, sha256 весов, время), машинно — `outputs/verify/verify_results.json`. Ожидаемый итог в консоли: `VERIFY: OK (18/18 checks passed)`.

3. Пакетная обработка собственных DICOM (папка монтируется только на чтение; сеть не нужна).

        docker run --rm --network none --cpus=2 --memory=3g --user "$(id -u):$(id -g)" \
          -v /path/to/dicoms:/data/input:ro -v "$PWD/outputs:/data/output" densitoai:2.4.0 batch

   Результат: `outputs/results.csv` (ровно 9 столбцов в порядке ТЗ: `path_to_study, study_uid, image_uid,
   anatomical_region, quality_class, violation_type, quality_prob, processing_status, time_of_processing`;
   несколько нарушений в `violation_type` разделены `;`), `outputs/results.xlsx`, технический `outputs/results_debug.csv`
   (измерения, текст ошибки для строк `Failure`), журнал `outputs/results.log` (имя журнала — `<output>.log`, флаг `--log-file`).

4. Воспроизводимость на собственных данных: тот же прогон через `verify --data` дважды даёт одинаковый CSV
   (без столбца time_of_processing) и печатает его sha256. Повторный запуск с `--expected-sha <sha>` завершится
   кодом 0 только при точном совпадении предсказаний.

        docker run --rm --network none -v /path/to/dicoms:/data/input:ro -v "$PWD/outputs:/data/output" \
          densitoai:2.4.0 verify --data /data/input
        docker run --rm --network none -v /path/to/dicoms:/data/input:ro -v "$PWD/outputs:/data/output" \
          densitoai:2.4.0 verify --data /data/input --expected-sha <sha из предыдущего вывода>

5. Проверить, что веса модели в образе — те, что заявлены в поставке (`models/WEIGHTS_SHA256.txt`).

        docker run --rm --network none densitoai:2.4.0 bash -c "cd /app && sha256sum -c models/WEIGHTS_SHA256.txt"
        docker run --rm --network none densitoai:2.4.0 bash -c "cd /app && python tools/hash_weights.py --check"

## Что именно проверяет `verify`

| Проверка | Критерий |
|---|---|
| Схема CSV | ровно 9 столбцов в фиксированном порядке |
| Полнота | число строк = число входных файлов (15 фантомов, в т.ч. 3 заведомо битых) |
| Идентификаторы | study_uid / image_uid равны тегам StudyInstanceUID / SOPInstanceUID |
| Обработка ошибок | Failure ровно для 3 битых файлов (обрезанные пиксели, без PixelData, не DICOM), остальные Success |
| Значения полей | quality_class ∈ {0, 1}, quality_prob ∈ [0; 1], status ∈ {Success, Failure}; class = 1 ⇔ violation_type не пуст; Failure только с class = 0 |
| Детерминизм | два прогона побитово совпадают во всех столбцах, кроме time_of_processing |
| Веса | sha256 `models/*.pkl`, `backbone_densito.pth`, `models_manifest.json`, `config.yaml`, EfficientNet-B0 совпадают с `models/WEIGHTS_SHA256.txt` |
| Согласованность моделей и конфига | вариант предобработки (К11) и источник эмбеддингов (К13) в `config.yaml` равны тем, с которыми обучены `.pkl` и записаны в `metrics_summary.json` |
| Словарь организаторов | строки `violation_type`, `anatomical_region`, разделитель `;`, имя колонки вероятности и размер пикселя совпадают с `schema/official_dictionary.json` |
| Эталон | классы совпадают с `tests/phantoms/expected_results.csv`, quality_prob в пределах ±0,001; отдельно (как замечание, не ошибка) — совпадение бит в бит по sha256 |
| Версия и config_hash | одни и те же во всех файлах поставки, доступных в образе (`tools/check_version_consistency.py`) |
| Безопасность API | результаты одного запроса не видны без его кода доступа, список запросов закрыт, пределы размера архива (`tests/test_api_security.py`) |
| Инвариантность к форме подачи | переименованная копия, zip, перемешанная вложенность и смешанный вход (папки + несколько zip) дают те же предсказания, нормализованный CSV совпадает побитово (`tools/transfer_check.py`) |
| Истинная геометрия фантомов | наклон, сдвиг, обрезка поля, область и сторона бедра совпадают с `tests/phantoms/MANIFEST.json` |
| Серия с визуализацией | DICOM Secondary Capture: производное изображение, ссылка на исходный снимок, надпись в пикселях, детерминированные UID |
| Стресс-набор входа | 24 случая битых и нестандартных файлов из фантомов (обрезанный, нулевой, не-DICOM, без PixelData/Rows/Columns/PixelSpacing, MONOCHROME1, 16 бит со знаком, RGB, 8×8, 4000×3000, Explicit VR BE, Deflated, RLE, JPEG Baseline, BitsStored 12, CT, постоянный кадр, zip с битым файлом, битый zip, вложенность 5, кириллица) в одном пакете с 15 фантомами: битые → одна строка `Failure` (class 0, violation пустой, prob 0.5), корректные кодировки → класс исходного фантома, строки нормы побитово равны одиночному прогону (`tools/stress_set.py`, `docs/STRESS_SET.md`) |
| Данные пользователя (`--data`) | строки = файлы, схема, sha256 предсказаний (+ сверка с `--expected-sha`) |

Без `--data` проверок ровно 18; в сборке образа 2.4.0 — `VERIFY: OK (18/18 checks passed)`. С `--data` добавляются 1–2 проверки
по данным пользователя. Что каждая проверка доказывает и какому пункту ТЗ отвечает — в разделе «Карта доказательств» ниже.

проверяет `python tests/test_evidence_map.py`.

| 21 | Данные пользователя: инференс завершился (только с `--data`) | п. 2.7 ТЗ на данных проверяющего (опция --data) | Если строка красная — инференс на ваших данных не создал CSV; смотрите журнал прогона, остальные проверки к вашим данным не относятся. |

Что этот отчёт не доказывает:

- **Качество на закрытых данных заказчика.** Отчёт проверяет формат, детерминизм, целостность поставки и геометрию на синтетических фантомах. Он ничего не говорит о ROC-AUC или F1 на закрытом тесте: эти числа есть только как оценка вне обучения (OOF, nested) на 499 обучающих снимках, см. docs/METRICS_REPORT.md.
- **Другой аппарат или другая выгрузка.** Все проверки идут на данных с одного денситометра (Lunar Prodigy, экспорт enCORE в DICOM CR, pixel spacing 1,05 × 0,6 мм). Работа на другом приборе или с другим экспортом не проверялась; такой снимок только помечается предупреждением «нестандартный источник снимка».
- **Клиническая корректность.** Зелёная таблица означает, что сервис выдаёт то, что заявлено, и делает это одинаково. Она не означает, что конкретное решение «нарушение / норма» верно клинически: критерии разметки заданы одним экспертом заказчика, сервис не ставит диагнозов и не заменяет решение врача.
- **Веб-кабинет и нагрузка.** Проверка безопасности API покрывает изоляцию запросов и пределы входа. Поведение под параллельной нагрузкой, время ответа при очереди и удобство кабинета отчётом не оцениваются.
- **Стресс-набор — синтетика, не реальные аномалии.** Случаи стресс-набора построены из синтетических фантомов и покрывают только перечисленные варианты кодирования и повреждения. Сжатия иных кодеков (JPEG 2000, JPEG-LS), многокадровые файлы, экспорт других аппаратов и реальные повреждённые выгрузки PACS набором не покрыты; ожидание для JPEG Baseline зависит от наличия декодера (Pillow) в окружении.

Эталонные значения поставки: sha256 предсказаний на фантомах
`39608a83a85839214b5d94bb7f575d558f7d5694261c4123a074c2ededefb0a7`; sha256 предсказаний на образце организаторов
(`tests/sample_test_zip`, 3 файла) `df0d9a94731d2589924170f06a6267caf0250507adfd60ce20da5de6aac93bec`.
Эти значения получены в стенде разработки (CPU x86-64, OMP_NUM_THREADS 1 и 2 дают одинаковый результат); на другом
процессоре возможны отличия quality_prob в последних знаках — тогда проверка эталона проходит по допуску ±0,001,
а побитовое сравнение фиксируется как предупреждение в отчёте.

## Поддерживаемые форматы DICOM

Измерено на 3 файлах образца (`docs/TRANSFER_SYNTAX_MATRIX.md`): Implicit/Explicit VR LE, Explicit VR BE, RLE Lossless,
JPEG 2000 Lossless (при установленных кодеках), 8 и 16 бит, MONOCHROME1/2, с PixelSpacing и без, без UID (генерируются
детерминированно), сырой поток без преамбулы — результат идентичен оригиналу. JPEG Lossless и JPEG-LS не проверены
(нет кодировщика в стенде).
На фантомах те же и дополнительные варианты (Deflated Explicit VR LE, 16 бит со знаком, RGB, BitsStored 12/16, JPEG
Baseline при декодере Pillow) проверяются стресс-набором `tools/stress_set.py` — класс и регион совпадают с исходным
фантомом (`docs/STRESS_SET.md`).

Отдельно от `verify` поверяется измерительный контур: `python tools/measurement_check.py` (~15 с на 2 vCPU, зерно
фиксировано) поворачивает 13 фантомов на −15…+15° и сдвигает их на −30…+30 мм в миллиметровых координатах
(PixelSpacing 1.05×0.6 мм) и сравнивает измеренное функциями `src/geometry_features.py` и `src/hip_features.py` с
заданным — без моделей, порогов и разметки. В заявленном диапазоне |угол| ≤ 8°, |сдвиг| ≤ 20 мм ошибки угла оси
позвоночника не выше 1.05° (MAE 0.35°), угла диафиза бедра — 0.09° (MAE 0.04°), смещения центра позвоночника —
0.26 мм, положения бедра относительно края кадра — 0.52 мм; сторона бедра верна в 245/245 кадрах. Акт с таблицами
«задано → измерено», пределами и описанием, где измерение ломается (угол оси при ≥ 10°, наклон одного столбика без
таза и рёбер, кость за краем кадра), — `docs/MEASUREMENT_CHECK.md`; `python tests/test_measurement_check.py` (~30 с)
проверяет пределы и детерминизм (`results_sha256` двух прогонов совпадает). Поверка на фантомах, не замена клинической
валидации.

Сравнение двух выгрузок регрессии (например, кандидата с эталоном предыдущей версии) — `tools/compare_regressions.py`:
строки сопоставляются по `image_uid`, сравниваются область, класс, состав типов нарушения, `quality_prob` и статус
(время не сравнивается); `--allow-types "Некорректная укладка"` и `--region "Поясничный отдел позвоночника"` задают,
какие изменения ожидаемы, любое другое различие даёт код возврата 1. Запуск:
`python tools/compare_regressions.py <кандидат.csv> <эталон.csv> --allow-types "Некорректная укладка" --region "Поясничный отдел позвоночника"`.

### Инвариантность к форме подачи данных и сверка с истиной фантомов

`verify` (и `docker run --rm --network none densitoai:2.4.0 verify`) дополнительно доказывает четыре вещи.

1. **Независимость от имён файлов, порядка и упаковки (прогон-двойник).** `tools/transfer_check.py`
   делает четыре копии входа и прогоняет инференс на каждой: `rename` — случайные имена файлов и
   каталогов (`f0000.dcm`, `s000/`); `zip` — та же копия одним архивом; `shuffle` — случайная
   вложенность 0–3 уровня, регистр расширений `.dcm/.DCM/.Dcm/без расширения`, кириллица, пробелы
   и скобки в именах; `mixed` — то же плюс три zip-архива с кириллическими именами в одном входе,
   один из них во вложенном каталоге. Предсказания сверяются с эталонным прогоном по ключу
   (`study_uid`, `image_uid`): `anatomical_region`, `quality_class`, `violation_type`,
   `processing_status` должны совпасть, `quality_prob` — бит в бит; с флагом `--bitwise` нормализованный
   CSV (без `time_of_processing` и `path_to_study`, строки отсортированы по ключу) должен совпасть по
   sha256. Флаг `--sr` дополнительно сверяет SR исследований после удаления только дат и времени
   создания. Это прямая проверка того, что отсутствие суффиксов `_ПОП/_ППОБ` в закрытом наборе ничего
   не меняет. Результат — файл `transfer_check.json` и строка проверки в `verify_results.json`; тот же
   прогон в виде теста — `tests/test_transfer_twin.py`. На 10 реальных исследованиях (46 снимков)
   все режимы дали побитово одинаковый CSV. Резервные идентификаторы для файлов без
   `StudyInstanceUID`/`SOPInstanceUID` считаются от sha256 содержимого файла и папки (а не от пути),
   поэтому переименование их не меняет; раскладывать файлы без `StudyInstanceUID` по разным папкам
   нельзя — они получат разные резервные `study_uid`. Пропустить проверку: `VERIFY_SKIP_TRANSFER=1`.
2. **Сверка с истинной геометрией.** `tests/phantoms/MANIFEST.json` хранит истинные параметры каждого
   фантома (наклон оси, положение центра, вариант дефекта, область). Проверка сравнивает с ними
   измеренные признаки: знак и величину наклона (допуск 6°), сдвиг центра, обрезку поля (кость у края поля, ≤ 6 мм),
   область «позвоночник/бедро» и сторону бедра. Металл на синтетических фантомах не проверяется:
   их «кость» сама яркая, порог по интенсивности на таких картинках срабатывает ложно. С версии
   фантомов 1.1 и правила `crop_aware` (`src/hip_features.py`) сторона и наклон проверяются строго,
   без известных отклонений: наклон при чисто боковом сдвиге 0.0° при истине 0°, сторона бедра
   верна на всех 8 фантомах, включая два с обрезанным полем (разбор — «Ограничения методологии»
   отчёта по метрикам, пункты 7 и 8).
3. **Серия с визуализацией (бонус ТЗ 2.6).** Проверка строит оверлей на фантоме и оборачивает его в
   DICOM Secondary Capture: требуются `ImageType = DERIVED/SECONDARY`, `SourceImageSequence` со ссылкой на
   исходный SOP Instance UID, `BurnedInAnnotation = YES`, панель с подписями под снимком и совпадение
   SOP/Series UID при повторном построении (детерминированность — иначе каждый прогон плодил бы новую
   серию в архиве). Файлы серии пишутся флагом `--sc-dir` (в API — каталог `sc/` папки запроса).
4. **Стресс-набор устойчивости входа.** `tools/stress_set.py` строит во временном каталоге копию 15 фантомов
   и подкаталог `stress/` с 24 случаями (список — `tests/stress/expected_stress.csv`, результаты — `docs/STRESS_SET.md`)
   и обрабатывает всё одним прогоном `src/inference.py --debug-csv`. Проверяется: код возврата 0, нет Traceback,
   9 колонок, строк ровно столько, сколько файлов (элементы zip считаются по одному, битый zip — одной строкой);
   у каждого случая статус равен ожидаемому; строки `Failure` оформлены как в `process_file` (class 0,
   `violation_type` пустой, `quality_prob` = `fallback_quality_prob` 0.5, UID непустые, причина в `results_debug.csv`);
   для корректных нестандартных кодировок регион, класс, тип нарушения и UID равны строке исходного фантома,
   |Δ quality_prob| ≤ 0.001; 15 строк фантомов в смешанном пакете побитово равны одиночному прогону (все колонки,
   кроме `time_of_processing`); время пакета ≤ 300 с (на стенде 2 CPU — около 8 с, огромный кадр 4000×3000 — 1,8 с).
   Ожидание для JPEG Baseline вычисляется по наличию декодера у pydicom (Pillow есть в образе → `Success`).
   Пропустить: `VERIFY_SKIP_STRESS=1`; размер огромного кадра: `VERIFY_STRESS_HUGE=2500x1500`.
   Тот же прогон в виде теста — `tests/test_stress_set.py`.
5. **Экспорт сегментации (дополнительный функционал, вне `verify`).** `python tests/test_segmentation_export.py`:
   файлы SEG/PNG/JSON для всех Success-фантомов и ни одного для Failure, `tools/validate_seg.py` PASS
   (обязательные теги, размер маски = Rows×Columns, ссылка на исходный снимок, число сегментов),
   детерминизм байт-в-байт при повторном прогоне, 9 колонок `results.csv` без изменений, мм = px × (0.6; 1.05).
   Устойчивость масок — `python tools/seg_stability.py --dataset <каталог> --n-studies 10 --out outputs/seg_stability.json`
   (Dice после сдвига яркости ±10 %, переворота и смены PhotometricInterpretation).
6. **Предложение коррекции области интереса и решения специалиста (дополнительный функционал, вне `verify`).**
   `python tests/test_roi_decisions.py`: `roi_suggestion` собирается для бедра и равен `null` для позвоночника, валидация
   решений («подтверждено» только при предложенной коррекции, «своя» — рамка внутри кадра), атомарное хранение
   `decisions.json`, выгрузка CSV, DICOM SR решений проходит `tools/validate_sr.py`, доступ по коду задачи (403/404,
   traversal); HTTP-часть через TestClient при наличии httpx (в образе его нет — эти проверки помечаются SKIP).
7. **Таблица бейзлайнов (вне `verify`).** `python tests/test_baseline_table.py` (~5 с): детерминизм
   `tools/baseline_table.py`, воспроизведение замороженных AUC/F1 стека по пяти критериям (допуск 1e-3) и F1 бинарной
   задачи по областям, ROC-AUC тривиальных бейзлайнов ровно 0.5, согласованность `docs/BASELINES.md` с `docs/baselines.json`.
8. **Кривая зоны «не уверен» (вне `verify`).** `python tests/test_uncertain_zone.py` (~7 с): инструмент
   `tools/uncertain_zone.py` отрабатывает во временный каталог, JSON валиден и без идентификаторов, SVG — корректный XML;
   монотонность по δ (доля строк в зоне, положительные в зоне, полнота с учётом зоны не убывают); текущая точка
   воспроизводит `metrics_summary.json -> uncertainty.row_uncertain_rate_by_region` (14.5 % / 9.4 %) и доли по критериям
   из `calibration.pkl`; два прогона дают одинаковый JSON. Полный отчёт — `docs/UNCERTAIN_ZONE.md`.
