## A. ЯВНЫЕ "не обязательно, но будет плюсом / здорово" пункты (приоритет для реализации)

Это прямая выборка мест, где участник спрашивает "нужно ли Х", а организатор отвечает "не обязательно, но будет хорошо/плюсом/бонусом". Каждый такой пункт — потенциальный источник дополнительных баллов.

## B. Критически важные уточнения формата ВЫХОДНЫХ ДАННЫХ (меняют реализацию)

1. **Гранулярность строк**: одна строка на каждое **изображение**, включая дубликаты (в датасете 499 файлов, но 252 уникальных изображения — тестовый набор так же может содержать дубли, каждый файл = отдельная строка) [716–753].
2. **violation_type — закрытый словарь**: организаторы **пришлют отдельно точный словарь** значений для `violation_type` (текст через `;`, если нарушений несколько; **пусто**, если нарушений нет — при этом `quality_class=0`) [780–830]. **ВАЖНО: нужно запросить/получить этот словарь у организаторов перед финалом**, иначе наша текстовая нотация не совпадёт с их скриптом проверки.
3. **Итоговое число типов нарушений: 5, а не 6** — для бедра "позиционирование/ротация" и вопрос ROI объединены в датасете в фактически 2 критерия (не 3 как в тексте ТЗ): **позвоночник — 3 критерия** (укладка, ось ≤5°, артефакты), **бедро — 2 критерия** (позиционирование+ротация объединены, и ROI-корректность) [897–952]. Наша текущая модель именно так и считает по бедру — это подтверждено правильным.
4. **quality_class при пропуске региона**: если у пациента нет снимка данной зоны — строку для этой зоны просто не создавать (это не "0", не "1", а "не применимо") [1420–1456].
5. **Разметка "Итог" в файле разметка.xlsx содержит ошибки агрегации** — организаторы сами это подтвердили и попросили ориентироваться **исключительно на отдельные критерии**, не на итоговую колонку [466–539]. Это прямое указание от организаторов, полученное уже после публикации датасета — **обязательно использовать это при переобучении/валидации моделей**, а не полагаться на агрегированный "Итог".
6. **Anatomical Region — будет присланный словарь русских названий**, не ориентироваться на DICOM-теги (могут быть неверны) [1511–1537].
7. **Оценка на закрытом тесте — двухэтапная**: (1) F1/метрика по бинарной классификации "есть нарушение / нет" на уровне изображения, (2) F1 macro-агрегированный по конкретным типам нарушений из словаря. Если решение верно определило "нарушение есть", но неверно указало тип — первая метрика растёт, вторая падает [1065–1142, 861–897].
8. **Угол оси позвоночника**: считается от **оси тел позвонков** (не от остистых отростков), от верхнего к нижнему видимому позвонку; ось сравнивается с **вертикалью кадра = осью сканирования (пиксели по Y)** [1578–1634].
9. **Сколиоз / клинические особенности НЕ считаются нарушением укладки** — если ось смещена из-за реальной анатомической деформации (сколиоз), это **не ошибка по критерию "ось"**, только явное отклонение относительно вертикали кадра оценивается [2189–2269]. Это прямое клиническое уточнение от врача-рентгенолога Смачковой — модель не должна штрафовать сколиозные случаи по критерию оси, если укладка сама была прямой.
10. **Чёрные прямоугольные маски по краям бедренных снимков — не значимый признак**, это защитное маскирование денситометра для мягких тканей, а не артефакт снимка; модель не должна обучаться на них как на сигнале [1638–1690].
11. **Pixel spacing для расчёта см**: аппарат не пишет Pixel Spacing в теги; организаторы сообщили физические размеры пикселя аппарата Lunar Prodigy Advanced: **Y = 1.05 мм, X = 0.6 мм** — можно использовать эти фиксированные значения для перевода критериев ROI (3см/2см) в пиксели, так как все данные (train + test) с одного и того же аппарата [331–441].
12. **Дубли изображений возможны и в закрытом тесте** — обрабатывать каждый файл отдельно.

## C. Организационные требования (для финальной подачи)

- Репозиторий с решением **обязательно публичный** (не приватный GitLab/GitHub) [276–291].
- Ссылку на решение прикладывать **заранее**, не в последний момент (риск перегрузки платформы) [153–180].
- Питч/защита ~5 минут + вопросы, но защищаются **только топ-10 команд**, прошедших первичную верификацию [291–312].
- Веса моделей — выложить либо прямо в репозитории, либо через ссылку на внешнее хранилище — открыто организаторам, но решение и способ проверки должны быть однозначны и легко воспроизводимы [2358–2455].
- Можно использовать любую платформу для хранения решения (не только Sourcecraft) [2358–2372].
- Внешние открытые датасеты и предобученные модели — разрешены, при условии, что финальное решение работает **полностью локально/офлайн**, без обращения к внешним API (в т.ч. запрещено использовать внешние LLM по API) [1273–1321].
- Тестирование будет на технических характеристиках сервера, указанных в ТЗ — не рассчитывать на более мощное железо [1345–1374].
- На закрытом тесте не будет посторонних (не спина/не бедро) изображений — но допускается защитная логика на этот случай [2278–2309].

## D. Ожидающиеся дополнительные материалы от организаторов (уточнить/получить, если возможно)

## E. Действия для нашей реализации (что делать по итогам анализа)

1. Исправить систему валидации/обучения, чтобы ориентироваться на **отдельные критерии `разметка.xlsx`**, не на агрегированный "Итог" — если ранее оффлайн-метрики (F1=0.51–0.62) считались по колонке "Итог", их нужно пересчитать по правильным целевым меткам.
2. Реализовать вывод `violation_type` как текстовый список через `;` по 5 категориям (3 спина + 2 бедро), пустая строка если нарушений нет.
3. Добавить (опционально, но рекомендовано) колонку с вероятностями нарушения — уже вычисляется моделью (sigmoid), просто нужно её сохранить в выходной xlsx/csv.
4. Строка на каждый файл/изображение (в т.ч. дубли) — не на уникальный study.
5. Не создавать строку для региона, если снимок этого региона отсутствует у пациента.
6. Учесть точные физические размеры пикселя (Y=1.05мм, X=0.6мм) при пересчёте критерия ROI (3см/2см) в пиксели вместо текущего relative-ratio подхода в auto_roi.py.
7. Не штрафовать за смещение оси при явном сколиозе относительно клинической нормы — критерий должен оценивать отклонение относительно вертикали кадра, а не "анатомическую правильность" позвоночника.
8. Игнорировать чёрные маски по краям бедренных снимков как признак при обучении/инференсе (проверить, что текущие фичи contour/artifact detection не реагируют на них ложно).
9. (Bonus) Реализовать детекцию/сегментацию белой разметки денситометра как отдельную опциональную фичу.
10. (Bonus) Добавить в Grad-CAM/визуализацию точечную локализацию структур (L1-L4, trochanter, femoral neck) — уже частично есть Grad-CAM, можно усилить.
11. (Bonus) Добавить простую защиту от "не позвоночник/не бедро" изображений (fallback processing_status).
12. Убедиться, что README/инструкция по запуску максимально просты для проверяющих — это прямо влияет на оценку по словам организаторов.
13. Подготовить финальный репозиторий как публичный.
