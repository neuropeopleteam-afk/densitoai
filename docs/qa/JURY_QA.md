# Вопросы жюри и ответы — DensitoAI 2.4.0 (дополнение 24.09)

Назначение: подготовка защиты на ЛЦТ 2026 (задача 4, заказчик ДЗМ / ЦДиТ). Ответы короткие, каждый — с файлом-источником в скобках; все числа взяты из документов репозитория и не пересчитывались. Разъяснения организаторов не пересказываются — см. `docs/qa/QA_COMPLIANCE_MATRIX.md`, `docs/qa/QA_WRITTEN_CLARIFICATIONS.md`, `docs/qa/QA_ANALYSIS.md`. Сценарии питча и демонстрации — `docs/qa/DEMO_SCRIPT.md`.

Правило ответа: сначала факт, потом цифра, потом ограничение. Если цифры нет в документах — говорим «не измеряли», а не оцениваем на глаз.

## 1. Соответствие ТЗ и формату выхода

**1.1. Что именно сдаёте по ТЗ и где это проверить?**
Контейнер Docker без сети, CLI и HTTP API пакетной обработки, CSV из девяти колонок в порядке ТЗ п.2.5 плюс XLSX, README с разделами по п.5 ТЗ, отчёт метрик с 95 % ДИ по п.8.4. Проверка формата встроена: `tests/test_inference_format.py` и поле `format_check` в ответе API. Сервис не медицинское изделие: строка о назначении стоит в конфиге, `/api/health` и на каждой странице кабинета — оценивается техническое качество, решение принимает врач (`README.md` §14, `docs/DZM_CONFORMANCE.md`, `web/index.html`).

**1.2. Как заполняются `anatomical_region` и `violation_type`?**
Только строки из разъяснений организаторов: «Поясничный отдел позвоночника» / «Проксимальный отдел бедра»; нарушения из закрытого перечня через «;», пустое поле при норме. Сторона бедра определяется внутри для выбора модели, в отчёт не выводится — так ответил организатор (`docs/qa/QA_WRITTEN_CLARIFICATIONS.md`, `README.md` §1).

**1.3. Что значит `quality_prob` и согласован ли он с `quality_class`?**
Смесь 0.5/0.5 отдельной модели «есть нарушение» и максимума скоров критериев, затем монотонное согласование: класс 1 тогда и только тогда, когда `quality_prob ≥ 0.5`. Противоречивых строк нет; в 2.0.x их было 79 из 499 (`README.md` §8).

**1.4. Укладываетесь ли в 3 минуты на исследование?**
Да. На боевом сервере (4 vCPU, Docker, один процесс) в тихих условиях 499 файлов обработаны за 368 с: медиана 0.54 с на файл, p95 1.76 с; тот же сервер под чужой нагрузкой — медиана 1.84 с, p95 6.11 с; локально на 2 vCPU — около 0.07 с (`docs/PERFORMANCE.md`). Через API с оверлеем и SR — 1.1–2.1 с на запрос (партия 10 файлов — 24 с стены). 499/499 файлов успешно, ноль необработанных исключений (`docs/METRICS_REPORT.md`, `README.md` §14).

**1.5. Что будет с битым файлом или чужой модальностью в закрытом тесте?**
Строка с `processing_status = Failure`, `quality_class = 0`, `quality_prob` < 0.5 (0.499999), партия продолжается. Инвариант «класс 1 ⇔ `quality_prob` ≥ 0.5» выполняется и для строки сбоя (см. 14.1). Проверено стресс-набором из 24 случаев (39 строк за 8.1 с) и 15 фантомами, из них 3 намеренно битых (`docs/STRESS_SET.md`, `docs/VERIFICATION.md`).

## 2. Данные и разметка

**2.1. Сколько у вас данных на самом деле?**
499 файлов, 100 исследований, 252 уникальных кадра: 247 файлов — побайтовые дубликаты внутри исследований, между исследованиями дубликатов нет. Позвоночник 166 файлов (99 исследований), бедро 329 (78 исследований; 4 файла исключены из 333). Метки внутри исследования согласованы: ICC позвоночник 1.00, укладка бедра 0.73, область интереса бедра 0.40 — поэтому единица счёта у нас исследование (`docs/sample_passport.md`, `docs/EVIDENCE.md` §1).

**2.2. Сколько положительных примеров по критериям?**
Файлы / исследования: укладка позвоночника 10/6, ось 17/10, посторонние предметы 35/17, укладка бедра 79/24, область интереса бедра 16/6. Бинарно: позвоночник 60 файлов из 31 исследования, бедро 92 из 28. Колонку «Итог» разметки не используем — она не совпадает с объединением критериев; метка «есть нарушение» — логическое ИЛИ по критериям строки (`docs/sample_passport.md`, `docs/EVIDENCE.md` §1).

**2.3. Один аппарат, один разметчик — что это значит для ваших выводов?**
Все снимки с одного GE Lunar Prodigy; шаг пикселя 1.05 × 0.6 мм задан организатором, тегов в файлах нет. Правила ТЗ в сантиметрах (не менее 2 см от края, 3 см над вертелом) считаем по этому шагу; если теги появятся — читаем их. Разметка одного эксперта, второго мнения нет, каппу измерить нельзя; эксперт, например, оценивает ось шире, чем глобальный наклон. Все метрики — про этот аппарат и этого эксперта, другой разметчик даст другие пороги (`docs/qa/QA_WRITTEN_CLARIFICATIONS.md`, `docs/sample_passport.md`, `web/docs.html`).

**2.4. Вы использовали внешние данные?**
Только без меток: пул из 15 633 фрагментов (FracAtlas, Arak, MTDDH, BUU-LSPINE, AASCE, DEXA-Osteo и наши 499 без разметки) для предобучения бэкбона, около 1.5 USD вычислений. Ни одна внешняя метка в классификаторы не попала; внешние наборы — ещё и тест на чужой домен (`docs/EVIDENCE.md` §2).

**2.5. Метка стороны бедра в разметке совпадает с вашим детектором стороны?**
Нет, расходится на 80 кадрах. Мы измерили чувствительность к этому: AUC области интереса бедра 0.917 при нашей стороне против 0.880 при стороне из разметки, F1 0.514 против 0.267; разницу даёт одно исследование из 5 кадров (`docs/METRICS_REPORT.md`, `docs/sample_passport.md`).

## 3. Метрики и честность

**3.1. Назовите главные цифры.**
OOF с группировкой по исследованию, 95 % ДИ бутстрапом по исследованиям (2000 повторов). «Есть нарушение»: позвоночник ROC-AUC 0.813 [0.69; 0.91], F1 0.662 [0.49; 0.80], macro-F1 по типам 0.547; бедро ROC-AUC 0.760 [0.63; 0.86], F1 0.516 [0.31; 0.68], macro-F1 0.473 (`docs/METRICS_REPORT.md`, таблица «Итого»).

**3.2. По критериям?**
ROC-AUC стека / F1: укладка позвоночника 0.893 / 0.500, ось 0.889 / 0.605, посторонние предметы 0.824 / 0.535, укладка бедра 0.725 / 0.432, область интереса бедра 0.917 / 0.514 (`docs/METRICS_REPORT.md`).

**3.3. Почему F1 низкий при высоком AUC?**
При 10–16 положительных файлах порог стоит на доле позитивов, и каждая ошибка стоит десятков пунктов F1. У укладки позвоночника интервал F1 [0.12; 1.00] — оценка описывает шесть конкретных исследований. AUC ранжирует все пары, поэтому устойчивее. Мы называем обе величины и интервалы (`docs/METRICS_REPORT.md`, `web/docs.html`).

**3.4. Что такое OOF и почему не train/test?**
Out-of-fold: каждое исследование предсказано моделью, которая его не видела, GroupKFold по исследованию. При 6 положительных исследованиях отложенный тест дал бы 1–2 позитива и ничего не измерил. Разбиение одно и зафиксировано; по 10 альтернативным разбиениям sd AUC 0.017–0.032, укладка позвоночника 0.860 ± 0.032, F1 области интереса бедра 0.352 ± 0.155. Производственное разбиение несколько благоприятнее среднего, и мы это пишем (`docs/METRICS_REPORT.md`, разделы «Разброс по разбиениям», `docs/EVIDENCE.md` §3).

**3.5. Как выбраны пороги и не подогнаны ли они?**
Правило порога выбиралось внутри nested GroupKFold 5 × 10: F1-оптимальный порог нестабилен (sd 0.09–0.13 против 0.03–0.04 у правил по доле позитивов). Принято: укладка позвоночника, укладка и область интереса бедра — доля позитивов; ось и предметы — доля позитивов × 1.4 (`docs/METRICS_REPORT.md`, раздел «Правило порога»).

**3.6. Чем вы лучше тривиальных бейзлайнов?**
На тех же OOF-строках: F1 «всегда нарушение» 0.09–0.39, AUC константы 0.5. Стек выше везде, но не везде выше сильнейшего контура: у укладки позвоночника контур A даёт AUC 0.915 при F1 0.00, у предметов контур B один даёт 0.897 против 0.823 у стека. Вес 0.5/0.5 фиксирован до измерений: подбор веса по пяти критериям на 6–17 позитивах — ещё пять параметров под выборку; вентильный вариант проверен nested и отвергнут (`docs/BASELINES.md`, `docs/NESTED_GATE_REPORT.md`).

**3.7. Калиброван ли `quality_prob`?**
Грубо: ECE (10 бинов) 0.139 позвоночник / 0.153 бедро, Brier 0.199 / 0.198 против 0.231 / 0.201 у константы. При `quality_prob ≥ 0.8` нарушение подтверждается у 80 % кадров позвоночника, при ≥ 0.9 — у 96 % кадров бедра. Внутри класса это ранг для очереди, а не процент. Скоры критериев — ранги по построению (ECE 0.26–0.45); Платт-величина `p_cal` есть только в техническом CSV и API и читается как вероятность лишь для предметов и укладки бедра. В официальный `quality_prob` калибровка не включена: `calibration.apply_to_quality_prob: false` (`docs/CALIBRATION.md`).

**3.8. Что такое зона «не уверен» и сколько в неё попадает?**
Строка спорная, если |скор − порог| ≤ запас; запас подобран по квоте 5 % на критерий. Хотя бы один спорный критерий — у 14.5 % строк позвоночника (24/166) и 9.4 % бедра (31/329). Класс и CSV не меняются, в кабинете строка помечена «Не уверен». Ошибки зона ловит частично: у укладки позвоночника запас 0 (10 строк OOF стоят ровно на пороге, 6.0 % при квоте 5 %, в зоне 10 из 14 ошибок), у оси — 0 из 17; перевороты от гаммы и шума зона не ловит (`docs/METRICS_REPORT.md`, раздел К3).

## 4. Методология изменений

**4.1. Как вы решаете, принимать ли изменение модели?**
Только по nested repeated GroupKFold: внешний цикл 5 фолдов по исследованию, повторов 10–20, внутри — весь выбор порога и признаков. Правило принятия — прирост AUC ≥ 0.03 во всех повторах и без падения macro-F1. На производственный OOF мы смотрели много раз — это риск подгонки под выборку, поэтому решения принимаются только nested, разбиение OOF не менялось, разброс по разбиениям опубликован (`docs/NESTED_GATE_REPORT.md`, `docs/EVIDENCE.md` §3).

**4.2. Что за «калиброванный гейт» и зачем он, если есть nested?**
Мы измерили ложное принятие старого правила на перестановках: 1–23 % (у укладки позвоночника 11–23 %), у t-теста 15–39 %. Новый парный гейт с ДИ и поправкой Холма по пяти гипотезам даёт 1–8 %. Он показал, что при 6 положительных исследованиях у нас нет мощности что-либо принять (`docs/NESTED_GATE_REPORT.md`, `tools/paired_gate.py`).

**4.3. Гипотеза H2 (голова укладки) гейт не прошла, но вы её включили. Как это объяснить?**
Честно. Nested 5 × 20: AUC укладки позвоночника 0.759 ± 0.031 → 0.878 ± 0.024, прирост +0.119, минимум по повторам +0.054, 20 из 20 ≥ 0.03, macro-F1 +0.079. Калиброванный гейт: ДИ90 [−0.004; +0.218], бутстрап p 0.12, знаковый тест p 0.008 — не принят, потому что при 6 положительных исследованиях интервал упирается в ноль. Решение о включении принял владелец продукта 23.09, это записано с временем. На закрытом тесте по этому критерию ждём результат слабее OOF (`docs/NESTED_GATE_REPORT.md` часть 5, `CHANGELOG.md` 2.4.0, `web/docs.html`).

**4.4. Что изменилось в 2.4.0 относительно 2.3.2?**
Только укладка позвоночника: контур A получил признак `synth_pos_logit`; AUC геометрии 0.681 → 0.915, стека 0.734 → 0.893, порог 0.822 → 0.861, F1 0.476 → 0.500, чувствительность 0.50 → 0.70, специфичность 0.96 → 0.93, флагов 11 → 18 на 166 строках. Бинарный AUC позвоночника 0.773 → 0.813. Бедро без изменений. Хэш конфигурации 5ac94710a6cd → 1f12392d7373 (`CHANGELOG.md` 2.4.0).

**4.5. Что вы отвергли и почему?**
Дообучение бэкбона под метки: −0.083 / −0.059 AUC, у соседних вариантов до −0.2. Вентильный стэкинг по критерию, идеи 12–15, калибровка в официальный `quality_prob`, альтернативные правила решения — не дали устойчивого выигрыша на nested или ломали согласованность класса и списка типов (`docs/NESTED_GATE_REPORT.md`, `docs/EVIDENCE.md` §3, `docs/METRICS_REPORT.md`).

## 5. Архитектура

**5.1. Как устроена модель?**
Два контура на каждый критерий. A — геометрия: сегментация кости, угол оси, смещение центра, доля ширины, площадь плотных включений, угол диафиза, расстояние до края, затем логистическая регрессия. B — замороженный EfficientNet-B0, 1280 признаков → PCA 32 → логистическая регрессия. Скоры переводятся в ранги по OOF и усредняются 0.5/0.5 (`README.md` §8, `web/docs.html`).

**5.2. Почему такая простая модель, а не свёрточная сеть конца в конец?**
252 уникальных кадра и 6–24 положительных исследования на критерий. Обучаемых параметров у нас десятки на критерий; сеть на таких данных заучит исследования. Проверили: дообучение бэкбона ухудшило AUC (`docs/EVIDENCE.md` §3, `docs/NESTED_GATE_REPORT.md`).

**5.3. Что за «синтетическая голова укладки без меток»?**
Малая сеть (Dropout → Linear 1280×256 → GELU → Linear 256×4, файл 1.3 МБ) над замороженным бэкбоном `densito`, обученная предсказывать искусственные сдвиги окна кадра — меток разметчика она не видела. Её логит — третий признак контура A для укладки позвоночника; отдельно её AUC на OOF 0.908. Бэкбон `densito` — EfficientNet-B0, дополнительно предобученный без меток на пуле из 15 633 фрагментов; для оси используется инвертированный вариант, для остальных критериев — ImageNet-веса. Отсутствие файла головы — ошибка при старте, не молчаливый ноль (`README.md` §8, `docs/NESTED_GATE_REPORT.md` часть 5, `docs/EVIDENCE.md` §2).

## 6. Продукт

**6.1. Что видит врач в кабинете?**
Партия сортируется по риску; в строке — область, класс, тип нарушения, `quality_prob`, пометка «Не уверен». В карточке — одно решение и одна главная причина, измерения против нормы (угол, мм), оверлей, слой «Сегментация», для бедра — предложенная область интереса. Режимы «Врач» и «Лаборант». Сайт https://neuropeople.pro (`README.md` §12, §14, `web/index.html`).

**6.2. Что есть в API?**
`/api/health`, `/api/analyze` (файлы и zip, ответ с `job_id` и кодом доступа), `/api/batch`, `/api/jobs/{job}`, `/api/results/{job}/{file}`, `/api/review`, `POST /api/results/{job}/decisions`, `GET /api/results/{job}/summary` (+ `.md`, `.csv`), список задач `/api/jobs` по админскому ключу, журнал исследований `/api/registry/*`, экспертная проверка `/api/expert/*`, Swagger `/docs` (`README.md` §6).

**6.3. Что такое DICOM SR у вас?**
Один Comprehensive SR на исследование, включая норму: вердикт, `quality_prob`, список нарушений, измерения в UCUM, кодировка `99DENSITO`, SHA-256 файла и пикселей, имя сервиса, версия, хэш конфигурации. Если пришла одна область из двух — нейтральное примечание о полноте (в обучающей выборке так устроено 22 исследования из 100). Валидатор `tools/validate_sr.py` (`docs/DZM_CONFORMANCE.md`, `README.md` §14).

**6.4. Приём снимков по DICOM — это работает?**
Storage SCP на pynetdicom: AE Title `DENSITOAI`, порт 11112, C-ECHO и C-STORE, CR/DX/SC, несжатые transfer syntax и RLE. Принятое исследование уходит в тот же `/api/analyze`. Без TLS, только внутренняя сеть отделения; принятые файлы хранятся в `inbox`, удаление включается настройкой. Тест — 42 проверки (`docs/DICOM_RECEIVER.md`).

**6.5. Что такое «сводка по партии»?**
Агрегаты для заведующего и старшего лаборанта без персональных данных: доли нарушений по области, типу, аппарату (хэш), дате; доля Failure с причинами; зона «не уверен»; UID для пересмотра. У каждой доли — ДИ Уилсона 95 % и пометка «мало данных» при n < 20. Форматы JSON / Markdown / CSV, 79 проверок (`README.md` §14, `docs/DZM_CONFORMANCE.md`).

**6.6. Что за экспорт сегментации и насколько он точен?**
DICOM Segmentation (кость и предметы для позвоночника; кость, поле сканирования, область интереса для бедра), PNG-маска и JSON с площадями и контурами в пикселях и мм. Маски — те же эвристики, что для измерений, не обученная сеть; эталона структур нет, поэтому Dice относительно эталона не измерен. Измерена только устойчивость: Dice 1.000 при переворотах, 0.999 / 0.996 при яркости ±10 % (`README.md` §14).

**6.7. «Предложение коррекции области интереса» — сервис меняет ROI аппарата?**
Нет и не может. Сервис измеряет дефицит поля сканирования в мм и предлагает область пунктиром; специалист выбирает «Подтвердить», «Отклонить» или «Своя», решение пишется в `decisions.json`, `decisions.csv` и отдельный SR решений с `VerificationFlag = UNVERIFIED` (специалист не аутентифицируется). Девять официальных колонок не меняются (`docs/DZM_CONFORMANCE.md`, `README.md` §14).

**6.8. Что делает кабинет со снимком чужой области или чужого аппарата?**
Предплечье, «всё тело», боковая проекция, чужая модальность, кадр вне геометрии 200–400 × 120–600 px — отказ по области без вердикта (44 проверки). Чужой аппарат (заполненный `Manufacturer`, явно не GE/Lunar) — отказ «аппарат вне области применения»: без этого правила на 904 PNG чужих аппаратов сервис давал 70–92 % «нарушений», с ним — 100 % отказов; на 499 файлах заказчика правило не срабатывает (`docs/EXTERNAL_DXA.md`). Чужой источник без тегов производителя — предупреждение «нестандартный источник снимка»: отпечаток тегов плюс расстояние Махаланобиса по эмбеддингам, FPR 1.0 % на OOF, 130/130 внешних кадров отбракованы. Девять колонок это не меняет (`docs/DZM_CONFORMANCE.md`).

**6.9. Что такое журнал исследований и зачем он отделению?**
Общий список всех загруженных исследований: поиск по ФИО, ID пациента, номеру направления, файлу и дате; фильтры по области, результату, статусу; статусы «нужна пересъёмка», «переснято», «принято», «спорно»; комментарии врача и лаборанта к исследованию или снимку. Лаборант отмечает «переснято», врач — любой статус. Хранение — SQLite в томе выходов, внутри контура учреждения, снимки не копируются (`README.md` §6, `src/registry.py`).

**6.10. Как отделение может само проверить сервис, не веря вам на слово?**
Экспертная проверка: заведующий формирует случайную выборку из журнала (половина с нарушением по решению сервиса, половина в норме), врач оценивает чистые кадры без отметок и без решения сервиса, отчёт по каждому критерию показывает совпадение, чувствительность и специфичность сервиса относительно врача с ДИ Уилсона и каппой Коэна, список расхождений, выгрузку CSV. Модель по ответам не дообучается. На демо-стенде — expert.neuropeople.pro (`README.md` §6, `src/expert_review.py`).

**6.11. Что будет, если на снимке осталась разметка денситометра (контуры ROI, линии L1–L4)?**
Организаторы предупредили, что на части снимков она есть. Мы её убираем до оценки: детектор тонких прямых линий включается только при ≥ 4 отрезках и закрашивает их по соседним пикселям. На 499 кадрах с синтетической разметкой смена класса без очистки 29,3 %, с очисткой 4,2 %; на кадрах заказчика очистка не срабатывает ни разу, регрессия 499 — без различий. Разметка в тесте синтетическая, цветные линии и подписи значений могут не пройти детектор — так и написано (`docs/MARKUP_STRESS.md`).

## 7. Безопасность и приватность

**7.1. Куда уходят снимки?**
Никуда. Сервис не делает внешних вызовов; самопроверка из 18 пунктов прогоняется в контейнере с `--network none`. Веса и кабинет лежат внутри образа; сеть нужна только на этапе сборки, образ переносится через `docker save`. Контейнер работает от непривилегированного пользователя `densito` (uid 1000) (`docs/VERIFICATION.md`, `web/docs.html`, `README.md` §13).

**7.2. Какие персональные данные вы обрабатываете и храните?**
В официальном CSV, SR и сводке по партии полей пациента нет — только UID, хэши файла и пикселей, хэш аппарата, даты исследования. Журнал исследований хранит ФИО, ID, дату рождения и номер направления для поиска — в базе внутри контура учреждения; в списке и в строках кабинета ФИО сокращено до «Иванова М. П.», ID — до последних цифр, полные данные открываются кнопкой, и каждый просмотр пишется в журнал доступа. На демо-стенде ФИО вымышленные, журнал закрыт паролем сайта. Логи приёмника без персональных данных; в документах и репозитории нет кадров пациентов. На сервере остаются `outputs/jobs/<job_id>/` (CSV, XLSX, оверлеи, SR, сегментация, решения) и `inbox` приёмника (удаление — `DENSITO_INBOX_KEEP=0`); автоматического срока хранения нет, политику задаёт отделение (`README.md` §6, §13, §14; `docs/DICOM_RECEIVER.md`).

**7.3. Как изолированы запросы разных пользователей?**
Каталог на запрос с проверкой имени `JOB_RE`, доступ к файлам только по коду задачи `job_token`, `_safe_job_file` против выхода за каталог, лимиты числа файлов и объёма загрузки, защита от Zip Slip. Тест `tests/test_api_isolation.py` — 88 проверок (`docs/DZM_CONFORMANCE.md`, `README.md` §6).

## 8. Воспроизводимость

**8.1. Как техническая группа проверит, что образ работает?**
`./build_and_run.sh build` собирает образ и запускает `verify`: 18 проверок — формат, детерминизм, sha256 весов, фантомы, стресс-набор, SR, SC-серия; итог `VERIFY: OK (18/18 checks passed)`. Офлайн: `tools/offline_check.sh` с `--network none`. Хватает 2 ядер и 3 ГБ, пик памяти 0.6 ГБ, GPU нет. Метрики пересчитываются `python src/eval_oof_metrics.py`, бейзлайны — `tools/baseline_table.py`, калибровка — `tools/calibration_report.py --bins` (`docs/VERIFICATION.md`, `README.md` §3–4, `docs/METRICS_REPORT.md`).

**8.2. Результат детерминирован?**
Да: два прогона одного входа дают побайтово одинаковый CSV без временных полей; ожидаемые хэши предсказаний на фантомах и на образце организаторов зафиксированы в `docs/VERIFICATION.md`. Хэши весов — `models/WEIGHTS_SHA256.txt`. Прогон-двойник — те же файлы переименованные, перемешанные, в zip и вперемешку с папкой — дал бит в бит тот же результат на 46 реальных кадрах; по пути убрали 3 зависимости от имени и порядка файлов (`docs/VERIFICATION.md`).

## 9. Ограничения и перенос

**9.1. Заработает ли на Hologic или другом Lunar?**
Не проверено на разметке, и мы этого не заявляем. Проверили поведение: на 904 снимках трёх внешних наборов (DEXA-Osteo, Arak, Chinese Osteoporosis) — 0 падений, но 70–92 % «нарушений», то есть чужой домен сервис не распознавал; теперь такие снимки получают отказ по аппарату (`docs/EXTERNAL_DXA.md`). Геометрические пороги и шаг пикселя зависят от аппарата; в README описана процедура перекалибровки. Чужой источник сервис помечает предупреждением (`README.md` §1, §11, §14; `docs/DZM_CONFORMANCE.md`).

**9.2. Насколько модель устойчива к искажениям?**
Формат и теги — 0 % переворотов класса; пиксельные искажения — заметные: на 81 размеченном кадре шум 3 % меняет класс у 27.2 %, гамма 0.7 — у 18.5 %, гамма 1.4 — у 17.3 %. На реальном потоке одного аппарата с фиксированным экспортом таких искажений нет; перевороты сосредоточены у порога (`docs/EVIDENCE.md` §5, `web/docs.html`).

**9.3. Какой критерий самый слабый?**
Укладка бедра: AUC 0.725, F1 0.432, чувствительность 0.44 — признаки ротации ловятся частично, специализированные признаки малого вертела и шейки остаются резервом. По укладке позвоночника результат формально высокий, но опирается на 6 исследований (`README.md` §10).

**9.4. Кто-нибудь из врачей проверял систему вслепую?**
Инструмент слепой ревизии готов (галерея «ответ до показа», 50 уникальных кадров, лист адъюдикации, пакет для врача), и в продукте есть экспертная проверка для отделения (вопрос 6.10). Сессия рентгенолога на момент сдачи не проведена. Это открытый пункт, мы его не выдаём за сделанный (`PLAN.md` К6, `docs/RADIOLOGIST_TEST_BRIEF.md`).

## 10. Клинические вопросы рентгенолога

**10.1. Что вы называете некорректной укладкой и как измеряете ось, не путая её с деформацией?**
Укладка: смещение позвоночника от центра кадра, отдел не полностью в кадре, неправильная доля ширины костной области — измеряем смещение и ширину и показываем против нормы. Ось — угол линейной аппроксимации центров строк костной маски к вертикали кадра — как разъяснил организатор: относительно вертикали, по телам позвонков. Деформацию не диагностируем и диагностических терминов в выводе нет; заметное искривление столба идёт только флагом в технический CSV (`docs/qa/QA_COMPLIANCE_MATRIX.md`, `PLAN.md` К7).

**10.2. Эндопротез или выраженная деформация — это «нарушение» у вас?**
По разъяснению организатора патология не является нарушением укладки. Подозрение на эндопротез отмечается отдельным флагом в техническом CSV и бейджем в карточке; в официальные типы нарушений не попадает (`docs/qa/QA_COMPLIANCE_MATRIX.md`, `PLAN.md` К9).

**10.3. Что вы предлагаете лаборанту делать с флагом?**
В карточке одна причина и одно действие: «Переснять сейчас» или «Показать врачу», плюс инструкция по повторной укладке (выровнять вдоль оси стола по лазерной метке; для бедра — ротация стопы внутрь с фиксатором, малый вертел почти не виден). Решение о повторном сканировании — за врачом (`web/index.html`, `README.md` §12).

**10.4. Сколько снимков врачу придётся смотреть глазами?**
На OOF в зоне «не уверен» 14.5 % строк позвоночника и 9.4 % бедра; они помечены и фильтруются в кабинете. Сколько это в потоке отделения — не измеряли, цифру экономии времени не называем (`docs/METRICS_REPORT.md` К3).

## 11. Сравнение с конкурентами

**11.1. Чем вы лучше других решений?**
Не сравниваем метрики: закрытый тест у всех один и считает его организатор. Отличия, которые можно проверить: единица счёта — исследование, учёт дубликатов, nested-протокол принятия изменений с опубликованными отвергнутыми гипотезами, образ без сети с самопроверкой, SR на исследование, приём по DICOM, сводка с интервалами (`docs/VERIFICATION.md`, `docs/NESTED_GATE_REPORT.md`, `docs/DZM_CONFORMANCE.md`).

**11.2. Ваши AUC ниже, чем у команды X. Почему?**
Спросите, как посчитано: по файлам или по исследованиям, с дубликатами или без, на одном разбиении или по nested. На наших данных 247 из 499 файлов — копии; счёт по файлам с утечкой копий между фолдами завышает любую метрику. Наши цифры — по исследованиям, с интервалами (`docs/sample_passport.md`, `docs/METRICS_REPORT.md`).

**11.3. Почему не показываете карты внимания, как другие?**
На этапе классификации у нас нет свёрточных активаций: контур A — измерения, контур B — замороженный бэкбон и логистическая регрессия. Показываем то, что измерено: контур кости, ось, границы области, плотные объекты и число против нормы (`README.md` §14).

## 14. Вопросы по итогам консилиума 24.09

**14.1. Строка Failure: какой у неё `quality_prob`?**
`quality_class = 0`, `quality_prob` < 0.5 (0.499999). Раньше было ровно 0.5, и оценщик, который берёт класс из вероятности по порогу 0.5, получил бы «нарушение» на битом файле, а на ROC-AUC такая строка вставала выше всех норм. Теперь инвариант «класс 1 ⇔ `quality_prob` ≥ 0.5» выполняется для всех строк, включая сбои (`src/inference.py`, `docs/STRESS_SET.md`).

**14.2. Фильтр чужого аппарата работает только в API?**
Нет, с 24.09 и в пакетном пути (CLI, `src/inference.py`): снимок не с GE Lunar Prodigy получает отказ, а не класс. Условие приёмки — 499 строк заказчика без изменений, сверка `tools/compare_regressions.py` с эталоном прогона (`docs/EXTERNAL_DXA.md`).

**14.3. Посчитайте метрики так, как посчитаем мы.**
`tools/organizer_metrics.py` берёт наш CSV из 9 колонок и разметку по исследованиям и считает F1 и ROC-AUC бинарной задачи по областям и общим пулом, F1 по пяти типам, macro-F1 в трёх трактовках — по файлам и по уникальным кадрам. Режим `--oof` сверяется с `docs/METRICS_REPORT.md` до третьего знака (`docs/ORGANIZER_METRICS.md`).

**14.4. Почему у вас метрики ниже, чем у команд со случайным разбиением?**
Ловушка клонов: из 499 файлов уникальных кадров 252. При случайном разбиении по файлам копия тестового кадра почти всегда есть в обучении, и модель узнаёт кадр, а не качество. На одной модели и одних признаках: при случайном разбиении AUC 0.92–0.99, при групповом 0.60–0.80, завышение +0.19…+0.33 (`docs/clone_trap.md`, `tools/clone_trap.py`, 10 сидов). Мы делим по группам «исследование + хэш пикселей».

**14.5. Сколько нормальных визитов получают тревогу?**
Половина. На уровне визита (100 визитов, 48 с нарушением) чувствительность 0.729 [0.60; 0.85], специфичность 0.500 [0.36; 0.64] (`docs/ORGANIZER_METRICS.md`). Поэтому решение сервиса — рекомендация с очередью по риску и зоной «не уверен», а не автоматическая пересъёмка.

**14.6. Не принимает ли сервис деформацию оси у пациента за плохую укладку?**
Частично да. У 14 исследований разметчик отметил деформацию оси, все размечены нормой по оси и укладке; на них 5 из 13 ложных срабатываний `sp_axis`: доля ложных 0.28 [0.06; 0.56] против 0.07 [0.01; 0.14] у прочих норм. Разность +0.21 [−0.02; 0.50], перестановочный p = 0.10 — сигнал устойчив по направлению, но на 14 исследованиях не доказан. Врач отклоняет такую пересъёмку в экспертной проверке; срез хранится как контрольный (`docs/AXIS_DEFORMITY_SLICE.md`, `data/slices/axis_deformity.csv`).

**14.7. Какая польза отделению, если не обещаете экономию?**
Кривая чистой пользы: решение сервиса лучше, чем «переснимать всех» и «никого», когда ложная пересъёмка дешевле пропущенного брака. На позвоночнике с 95 % ДИ — при цене ложной пересъёмки 0.4–0.7 от пользы пойманного нарушения; на бедре выигрыш есть по точечной оценке, но ДИ задевает ноль. В рабочей точке (`quality_prob` ≥ 0.5) польза 8.4 и 0.6 на 100 кадров. Экономию и пропускную способность не измеряли (`docs/DECISION_CURVE.md`, `docs/decision_curve.svg`).

**14.8. Не учится ли модель на метаданных, размере кадра или порядке файлов?**
Проверили отрицательными контролями: модели только на метаданных, экспозиции, размере кадра, числе файлов, порядке строк и UID-хэше при той же групповой проверке. На бинарных задачах обеих областей ни один контроль не превысил нулевую полосу перестановок; при перемешанных метках стек изображения даёт AUC около 0.5, то есть протокол утечку не пропускает. Сработали 2 контроля из 42, оба объяснены: версия ПО экспорта связана с долей артефактов позвоночника (модель её не видит, различение внутри версий сохраняется) и размер кадра для `hip_roi` — это длина скана, суть критерия. Честно: сигнал укладки бедра в основном уровня визита, сторону внутри визита модель различает плохо (`docs/SHORTCUT_AUDIT.md`).

**14.9. Почему не использовать другое бедро того же визита для укладки бедра?**
Проверили и отвергли. На сохранённом OOF прирост выглядел как +0.049…+0.071 AUC, но это оценка поверх готовых предсказаний. Полный протокол с переобучением моделей в каждом фолде (5×20×3, кандидаты объявлены заранее) дал: w по внутренним фолдам +0.021 (8 из 20 повторов ≥ 0.03), w = 0.3 +0.022 (5 из 20), solidity другого бедра +0.039 (13 из 20, неустойчив к удалению одного исследования); калиброванный гейт с поправкой Холма не принял ни одного. Около 0.02 AUC — оптимизм сохранённого OOF. Поставка не изменилась (`docs/NESTED_GATE_REPORT.md`, часть 7; `docs/k5/B1_PREREGISTRATION.md`).

**14.10. Почему не использовать факт пересъёмки как признак (М3)?**
Отвергнуто: в данных нет ни одной пересъёмки. Все повторы — побайтовые клоны экспорта, в 150 из 150 пар «исследование × сторона» один уникальный кадр; AUC признака «число файлов» 0.55 (`PLAN.md`, «План на победу»).

**14.11. Как вы определяете сторону бедра, если в DICOM её нет?**
Анатомическим детектором по изображению: в 74 из 74 исследований с двумя бёдрами он даёт правое и левое (плотностная эвристика — 57 из 74), обучение идёт на метках по детектору (К5 19.09, `docs/K5_HIP_POS_AXIS_REPORT.md`). Цена ошибки стороны видна на `hip_roi`: F1 0.514 при метке по детектору и 0.267 по метке разметки — разницу дают 5 кадров одного исследования, показываем обе (`docs/metrics_side_label.json`).

**14.12. Можно ли передать модель заказчику как есть?**
Нет. Исследовательский прототип: бэкбоны `sp_pos` (`densito`) и `sp_axis` (`densito_inv`) дообучены на пуле с некоммерческими лицензиями (Arak — CC BY-NC, BUU-LSPINE — EULA). Для передачи заказчику — вариант `densito_inv_free` (`models/backbone_densito_inv_free.pth`, без этих наборов), цена измерена на nested-протоколе: `sp_axis` AUC стэка 0.860 → 0.773 (`docs/EMB_GATE_REPORT.md`); для `sp_pos` `densito_inv_free` не измерен, замена на `imagenet` стоила 0.759 → 0.672 (К13, до H2).
