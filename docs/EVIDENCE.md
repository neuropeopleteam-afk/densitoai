# Доказательная база DensitoAI v2.4.0

Один документ о том, откуда данные, как считались числа и что не подтвердилось. Каждое число — из файла проекта,
источник указан в скобках. Все метрики — out-of-fold (OOF); ничего не измерено на закрытом тесте организаторов.

## 1. Происхождение данных

- Обучающий набор организаторов: **499 DICOM-файлов, 100 исследований**, разметка — xlsx организаторов
  (`HANDOVER.md` §9; `data/labels_full.csv`, `data/labels_for_embeddings.csv`). Ключ соединения — папка исследования.
- Прибор один — **GE Lunar Prodigy**, все снимки сделаны в Москве на одних аппаратах (слова владельца, `HANDOVER.md` §9;
  QA_COMPLIANCE_MATRIX №1: pixel spacing Y = 1.05 мм, X = 0.6 мм, тегов в DICOM нет). Ширины кадра: 300 px позвоночник,
  280/248 px бедро (`config.yaml → regions.standard_cols`).
- Уникальных кадров по md5 пикселей — **252 из 499**; остальные 247 — побайтовые дубликаты внутри исследований, ни один
  хэш не встречается в двух исследованиях (`docs/IMPROVEMENT_ANALYSIS.md` §2). Поэтому группировка по исследованию
  исключает утечку дубликатов между обучением и валидацией.
- Разметка: один разметчик; столбец «Итог» организаторы назвали ошибочным — истина берётся из отдельных критериев,
  метка «есть нарушение» = OR критериев (`docs/qa/QA_COMPLIANCE_MATRIX.md` №9; `src/build_dataset.py`).
- Число валидных снимков и позитивов по критериям (`models/metrics_summary.json`): позвоночник n = 166 —
  sp_pos 10, sp_axis 17, sp_art 35; бедро n = 329 — hip_pos 79, hip_roi 16 (правое 7, левое 9). Бедро: 333 кадра в
  `data/labels_hip_canonical.csv`, 4 без применимой разметки исключены (`docs/IMPROVEMENT_ANALYSIS.md` §2).
- **Паспорт выборки** (`docs/sample_passport.json`, `python tools/sample_passport.py`; единица наблюдения —
  исследование, метка задана организаторами на исследование, для бедра — на исследование и сторону).
  Файлов 499, исследований 100, уникальных кадров по хэшу пикселей 252 (247 дубликатов — клоны экспорта внутри
  исследования, ни один хэш не встречается в двух исследованиях). Обе области есть в 78 исследованиях, только
  позвоночник — в 21, только бедро — в 1. Кадров бедра 333: по стороне из разметки 172 правых / 161 левых, по
  детектору стороны 164 / 169 (расходятся на 80 кадрах); с применимой разметкой стороны 329.

  ICC — внутрикластерная корреляция метки внутри исследования (ANOVA-оценка для бинарного исхода), DEFF = 1 + (m − 1)·ICC,
  n_eff = файлы / DEFF. Для позвоночника ICC = 1: метка постоянна внутри исследования, и 166 кадров несут информацию
  99 исследований. Для бедра кластер — исследование, а метка задана на сторону, поэтому n_eff лежит между числом
  исследований и числом кадров; читать его нужно вместе с числом положительных исследований (hip_roi — 6).
  Концентрация: у sp_pos и hip_roi половину всех положительных кадров дают 2 исследования, 80 % — 4; у sp_art одно
  исследование даёт 10 из 35 положительных кадров. Поэтому F1 и AUC этих критериев описывают, как классифицированы
  несколько конкретных пациентов, а не устойчивую способность распознавать дефект.

## 3. Протокол валидации

- Обучение и OOF-оценка: `src/train_stacked.py` — repeated GroupKFold по исследованию (`README.md` §структура:
  «5×5 GroupKFold»); снимки одного исследования никогда не оказываются одновременно в обучении и валидации
  (`docs/METRICS_REPORT.md`).
- Доверительные интервалы: study-level percentile bootstrap, 95 %, 2000 повторов (`docs/METRICS_REPORT.md`;
  `src/eval_oof_metrics.py`).
- Пороги — только по OOF: `threshold_rule` в `models/metrics_summary.json` (правило К3: `prevalence` для sp_pos,
  hip_pos, hip_roi; `prevalence_x1.4` для sp_axis, sp_art; общая hip-модель для сторон; F1-оптимальный порог
  `f1_optimal_oof` не используется с 2.2.0). Те же пороги использует инференс
  (`config.yaml → thresholds: null` → metrics_summary).
- Стекинг: ранговое усреднение перцентилей geom/emb 0.5/0.5 относительно OOF-распределения
  (`config.yaml → stacking`; `models/oof_stacked_*.csv`).
- Nested-валидация: правило порога (К3), вес вентиля (К2), вариант предобработки (К11), источник эмбеддингов (К13) и
  признак головы укладки (H2) выбирались внутри nested repeated GroupKFold (`docs/METRICS_REPORT.md`, разделы «Правило
  порога» и «Nested», `docs/NESTED_GATE_REPORT.md`; поля `nested_*` в `metrics_summary.json`). Что **не** сделано:
  сам порог по-прежнему считается по доле позитивов на всём OOF (внешнего контура для значения порога нет), веса
  стекинга 0.5/0.5 зафиксированы заранее и не выбирались.

### H2 (2.4.0, 23.09): признак головы укладки в контуре A sp_pos

Признак контура A `synth_pos_logit` — логит головы, обученной на синтетических смещениях кадра без меток
(`models/head_densito_synth.pth`, `src/sppos_head.py`); вход — канонический эмбеддинг `densito`, который контур B
sp_pos уже считает. Принят по действующему правилу nested (ΔAUC +0.119, 20/20 повторов; контроль с OOF-скором головы и
с финальной головой, стоящей в продакшене, — +0.119 и +0.113); калиброванный гейт при 6 положительных исследованиях не
имеет мощности (ДИ90 [−0.004; +0.218] упирается в 0, p 0.12, sign-flip p 0.008) — это указано явно, решение владельца.
Итог по OOF: sp_pos AUC geom 0.681 → 0.915, стек 0.734 → 0.893, порог 0.822 → 0.861, F1 0.476 → 0.500; бинарная
метрика позвоночника ROC-AUC 0.773 → 0.813, F1 0.623 → 0.662, macro-F1 0.539 → 0.547. Остальные критерии и бедро
воспроизводят прежние числа (`docs/NESTED_GATE_REPORT.md`, часть 5; `models/nested_gate_decisions.json`).

**Регрессия на 499 файлах (образ `densitoai:2.4.0`, `src/inference.py`, 23.09, сервер 4 vCPU, тихие условия).**
499 строк, 0 отказов, формат выгрузки проверен; сравнение с выгрузкой 2.3.2 по `image_uid` (колонки
`anatomical_region`, `quality_class`, `violation_type`, `quality_prob`, `processing_status`): изменились **50 строк,

2 «нарушение → норма»), ещё у 2 строк при том же классе добавился или исчез тип «Некорректная укладка» в списке
типов; все 7 изменений касаются только критерия `sp_pos`, остальные типы нарушений в этих строках сохранились.

строки позвоночника из 15: фантом `study_04/CR000000.dcm` варианта `shifted` (силуэт сдвинут относительно поля сканирования)

### К11 (20.09): вариант предобработки по критерию

Принято: канонизация экспозиции (один параметр γ к эталону обучающей выборки) для критериев укладки:
sp_pos (nested выбрал её в 44/49 фолдов, средний ΔAUC +0.028, контур B ещё +0.021), hip_pos (30/50, +0.002).
Отвергнуто для sp_axis (ΔAUC −0.003 / −0.023), sp_art (−0.019 / −0.030), hip_roi (−0.029 / −0.003) — у посторонних
предметов и ROI абсолютная плотность является сигналом, и канонизация его стирает. Выигрыш по устойчивости:
перевороты при гамме 1.4 — 39.5 % → 17.3 %, при гамме 0.7 — 25.9 % → 21.0 % (`docs/ROBUSTNESS_REPORT.md`).
Полный протокол и числа — `docs/PREPROC_GATE_REPORT.md`, `models/preproc_gate_decisions_{a,b}.json`.

### К12 (20.09): подавление шума денойзингом в предобработке — отвергнуто

Проверялось, можно ли убрать перевороты класса при гауссовом шуме σ = 3 % (27.2 % кадров из 81) мягким
денойзингом перед признаками и перед эмбеддингами. Ядро выбиралось замером, а не на глаз: median 7×7
снижает косинусный дрейф эмбеддинга при шуме 0.221 → 0.071 за 0.0039 с/кадр, non-local means даёт то же
(0.076) в 19 раз дороже, гаусс и bilateral отброшены (0.232 — не лучше, чем без фильтра). Дополнительно
подтверждён механизм: если порог Otsu в `segment_bone` считать только по пикселям тела, дрейф признака
`metal_area_mm2` при шуме падает 0.256 → 0.061 σ, а AUC признака `axis_angle_deg` растёт 0.839 → 0.895.

Что показал nested (5 фолдов × 10 повторов, группы — компоненты связности study/pixel_hash):

| Конфигурация | Шум σ 3 % | Обрезка 4 % | resize ×1.25 | Время | Решение |
|---|---|---|---|---|---|
| 2.2.0 (в проде) | 27.2 % | 16.0 % | 8.6 % | 0.05 с | — |
| `sp_axis` контур A → `denoise7` (единственный прошедший стадию a: 39/50 фолдов, ΔAUC +0.024, Δmacro-F1 +0.032) | 28.4 % | 14.8 % | 8.6 % | 0.05 с | **отвергнуто** |
| `denoise7` во всех контурах | **12.3 %** | 22.2 % | 14.8 % | 0.08 с | отвергнуто |
| `denoise` 3×3 во всех контурах | 19.8 % | 14.8 % | 17.3 % | 0.08 с | отвергнуто |

Почему отвергнут даже прошедший гейт вариант: критериальный AUC `sp_axis` растёт 0.738 → 0.766, но F1
критерия не меняется (0.381), macro-F1 позвоночника не меняется (0.464), а первая метрика организаторов —
бинарная «есть нарушение» — проседает: ROC-AUC 0.758 → 0.743, F1 0.609 → 0.584. Оба сдвига лежат внутри
доверительных интервалов (± 0.12), то есть выигрыша нет ни на одной оцениваемой метрике, а сложность
растёт: новый вариант предобработки, отдельные файлы признаков и эмбеддингов, +0.0039 с на кадр.
Конфигурация, которая действительно лечит шум (денойзинг всем контурам), стадию b не прошла
(`sp_art` ΔAUC −0.031, Δmacro-F1 −0.054) и портит инвариантность к обрезке и масштабу (+6.2 п.п. к обеим)
при росте времени на 60 %. Вывод для защиты: перевороты при шуме сидят в контуре B критериев `sp_art` и
`hip_pos`, и на этой выборке (n_pos 35 и 79) лечение обходится дороже болезни.

### К13 (20.09): источник эмбеддингов контура B по критерию — принято одно изменение из пяти

GPU-эксперимент обучил два бэкбона EfficientNet-B0 с loss инвариантности эмбеддинга к гамме и шуму:
`densito_inv` (полный пул 15 633 плитки) и `densito_inv_free` (9 893 плитки без данных с несвободной
лицензией). На его собственной оценке (только контур B) прирост выглядел крупным сразу на двух критериях
(`sp_axis` +0.279 AUC, `hip_pos` +0.131), но там бэкбон и выбирался, и оценивался на одной выборке. Решение
принималось заново внутри nested CV на полном стеке (`tools/emb_gate.py`, 5 внешних фолдов × 20 повторов,
3 внутренних, порог по правилу на inner-OOF).

| Критерий | Было | Кандидат | nested ΔAUC стэка | Прирост ≥0.03 | Решение |
|---|---|---|---|---|---|
| `sp_axis` | imagenet | `densito_inv` | **+0.111** | 19/20 повторов (в плюсе 20/20) | **внедрено** |
| `hip_pos` | imagenet | `densito_inv` | +0.007 | 6/20 | не принято |
| `hip_pos` | imagenet | `densito_inv_free` | −0.005 | 1/20 | не принято |
| `sp_art` | imagenet | лучший из трёх | −0.045 | 1/20 | не принято |
| `hip_roi` | imagenet | лучший из трёх | −0.009 | 3/20 | не принято |
| `sp_pos` | densito | imagenet | −0.087 | 1/20 | оставлен `densito` |

Результат внедрения на `sp_axis`: контур B 0.491 → 0.797, стек 0.738 → 0.889, F1 OOF 0.381 → 0.605,
nested AUC 0.748 → 0.860, nested F1(+) 0.223 → 0.433. Бинарная метрика организаторов по позвоночнику
выросла: ROC-AUC 0.758 → 0.773, F1 0.609 → 0.623, macro-F1 по типам 0.464 → 0.539. Бедро не затронуто.
Устойчивость сервиса в целом почти не изменилась (гамма 0.7: 21.0 % → 18.5 %, шум σ = 3 %: 27.2 % → 27.2 %) —
в полном решении перевороты дают другие критерии (К12), а инвариантный бэкбон стоит только на `sp_axis`.
Полный протокол и числа — `docs/EMB_GATE_REPORT.md`, `models/emb_gate_decisions.json`.

## 5. Известные ограничения

- **Мало позитивов**: sp_pos 10 файлов / 6 исследований, sp_axis 17 / 10, ROI бедра 7 (правое) + 9 (левое) = 16 файлов
  на 6 исследованиях (`models/metrics_summary.json`; число исследований — паспорт выборки, §1, `docs/sample_passport.json`);
  ДИ F1 для sp_pos [0.12; 1.00], для hip_roi [0.00; 0.91], для rh_roi/lh_roi [0.00; 1.00] (`models/metrics_summary.json`, пометка
  «ненадёжно: <10 позитивов»).
- **Один разметчик**, межэкспертного согласия нет; двойная разметка запланирована, не выполнена
  (`docs/IMPROVEMENT_ANALYSIS.md` §3).
- **Чувствительность к яркостной кривой и шуму** (`docs/ROBUSTNESS_REPORT.md`, `docs/qa/robustness_results.json` от 20.09,
  81 снимок, версия 2.2.0 после К13; стресс-тест на 60 файлах в `docs/METRICS_REPORT.md` — другая выборка и сборка 19.09):
  доля смены класса — гауссов шум σ = 3 % 27.2 % (22/81), гамма 0.7 18.5 % (15/81), гамма 1.4 17.3 % (14/81),
  resize ×0.8/×1.25 19.8 %/8.6 %, обрезка 4 % 16.0 %; формат-инварианты (пересохранение, удалённые теги,
  нет UID, MONOCHROME1, 16 бит) — 0 %.
  У 57–76 % перевернувшихся запас |score − порог| < 0.15. Область (spine/hip) не менялась ни в одном сценарии.
- **`quality_prob` — грубая вероятность, не точная**: смесь any-модели и максимума скоров критериев, согласованная с
  классом; на OOF ECE (10 бинов) 0.14 / 0.15 и Brier 0.199 / 0.198 (позвоночник / бедро) против 0.231 / 0.201 у
  константы, наклон рекалибровки 0.80 / 0.58; ранговые скоры критериев вероятностями не являются
  (`docs/CALIBRATION.md`, `docs/calibration/calibration.json`; `calibration.apply_to_quality_prob: false`).
- **Один прибор, одна организация**: на других денситометрах пороги геометрии могут требовать перекалибровки
  (`README.md` §14); OOD-детектор чужого аппарата реализован как предупреждение, а не отказ (`src/extras.py: OODGate`,
  `models/ood_gate.pkl`, `docs/OOD_GATE_REPORT.md`: FPR 1,0 % на OOF, 130/130 внешних кадров отбракованы; флаг
  `ood_flag` в `results_extras.csv` и API, девять колонок CSV не меняет).
- **Локализация структур не валидирована** (нет Dice/IoU); оверлей показывает измеренную геометрию, а не проверенную
  сегментацию (`docs/IMPROVEMENT_ANALYSIS.md` §3 «§8.3»).
- Скорость: локально p50 0.04 с, p95 0.07 с на снимок без бонусов (`docs/ROBUSTNESS_REPORT.md`, identity); на боевом сервере в тихих условиях — медиана 0,54 с на снимок, p95 1,76 с (499 файлов за 368 с одним процессом); под чужой нагрузкой — медиана 1,84 с, p95 6,11 с (выгрузка 2.3.2); локально на 2 vCPU — порядка 0,07 с
  (`docs/PERFORMANCE.md`); второй бэкбон для позвоночника ≈ +0.3 с/файл (`docs/GPU_EXPERIMENT.md`).
