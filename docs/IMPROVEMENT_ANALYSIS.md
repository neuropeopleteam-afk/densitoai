# DensitoAI — анализ улучшений и «фишек» для победы (18.09.2026)

Источники: независимое ревью другой модели (`docs/INDEPENDENT_REVIEW_2026-09-18.md`,
GPT-5.6, роль «скептичный член жюри»), собственный разбор кода и метрик, критерии ТЗ §8.1–8.5,
разъяснения организаторов (`docs/qa/`). Числа ниже перепроверены по данным, а не взяты со слов.

## 1. Вердикт в десяти строках

1. Обязательная часть закрыта полностью и аккуратно; инженерно продукт сильнее среднего.
2. Главная уязвимость — не отсутствие фишек, а доказательная база: 100 исследований,
   252 уникальных кадра (остальные 247 — побайтовые дубликаты внутри исследований), один разметчик.
3. Редкие классы держатся на нескольких пациентах: `sp_pos` — 10 позитивов из 6 исследований,
   `hip_roi` — 16 позитивов из 6 исследований. Жюри это спросит.
4. Пороги, веса стэкинга и признаки выбирались по тем же OOF, на которых показаны метрики —
   model-selection bias; nested CV пока нет.
5. `quality_prob` — ранговый скор, согласованный с классом, а не калиброванная вероятность.
6. Чувствительность `hip_pos` 0.43: пропускаем больше половины ошибок укладки бедра.
7. API имеет углы: небезопасная распаковка zip, общие каталоги бонусов между запросами,
   коллизии одинаковых имён файлов.
8. Веб-интерфейс — «инженерное демо», а не рабочее место врача: нет очереди по риску,
   подтверждения, карточки решения, XLSX.
9. Победная стратегия: превратить каждую слабость в демонстрируемую сильную сторону —
   честность, надёжность, клинический сценарий «второй читатель», ценность для отделения.
10. Метрики на закрытом тесте мы уже почти не сдвинем; сдвинем оценку по §8.1, §8.2, §8.3, §8.5.

## 3. Слабые места глазами жюри (кратко)

- **§8.1 Подход.** Один разметчик, нет межэкспертного согласия; редкие классы на 3–6
  пациентах; выбор порогов на OOF без вложенной валидации; медианы импутации считаются до
  разбиения на фолды. Ответ: nested group-CV, честная model card, план двойной разметки в пилоте.
- **§8.2 Техника.** Zip Slip / zip-bomb; общие каталоги бонусов и коллизии `stem`; `/api/results`
  отдаёт любой файл из общего каталога; `/api/batch` принимает произвольные пути; сжатые
  transfer syntax не гарантированы; противоречивые цифры скорости в разных документах.
- **§8.3 Соответствие.** ТЗ говорит о «корректности разметки анатомических структур», у нас
  нет валидированной локализации (Dice/IoU/keypoints). «Самостоятельное изменение области интереса» — по сути
  рекомендация о недостаточности поля сканирования; так и надо называть.
- **§8.4 Эффективность.** Средние F1/AUC, слабые редкие классы, «вероятность» не калибрована,
  нет Brier/ECE/reliability, нет неопределённости отдельного предсказания.
- **§8.5 Питч.** Слишком много артефактов, нет одного клинического сценария от лаборанта до
  заведующего; план пилота без endpoint и ответственных.

## 4. Удобство: быстрые правки (каждая ≤ 2 ч)

1. Веб: кнопка «Скачать XLSX» (backend уже умеет, UI не передаёт `xlsx=true`).
2. Веб: сортировка таблицы по риску, фильтры «нарушения / норма / ошибки», группировка по исследованию.
3. Веб: человеческая ошибка вместо сырого HTTP-текста; экранирование имён файлов (сейчас `innerHTML`).
4. Веб: индикатор прогресса при загрузке партии; счётчик «обработано N из M».
5. XLSX: лист «Сводка», закреплённая шапка, автофильтр, подсветка `Failure` и `quality_class = 1`.
6. Debug-CSV: колонки `error_code`, `action` («принять / проверить / переснять»), `model_version`.
7. Документация: единый benchmark скорости (p50/p95 wall time, cold/warm, с бонусами/без);
   объяснить 333 → 329; убрать противоречия из разных ревизий README.
8. API: `/api/v1/` префикс, `request_id`, версия модели и хэш конфига в каждом ответе.

## 6. Предлагаемый план «11 из 10» (порядок исполнения)

**День 1 — доверие.** (1) честный риск + зона отказа + калибровочный отчёт; (2) стресс-тест
и hardening API; запустить (4) nested CV в фоне. Переформулировать документы по §7.
**День 2 — сценарий.** (3) карточка решения + очередь + подтверждение + audit log; (7) режим
лаборанта; (5) панель отделения; быстрые правки §4.
**День 3 — внедрение и локализация.** (6) OOD gate; (8) watch-folder / C-STORE + проверка SR
в Orthanc; (9) micro-gold с рентгенологом по `docs/RADIOLOGIST_TEST_BRIEF.md` — если найдётся врач.
Пункты 10–12 — только при остатке времени.

Питч после этого строится вокруг одного сценария: лаборант закончил скан → за 2 с вердикт с
причиной и измерением → при неопределённости — очередь врачу → врач подтверждает одним кликом →
заведующий видит отчёт причин брака по отделению → подтверждения идут в дообучение.

## 7. Что переформулировать, чтобы не подставиться

- «Вероятность» → «ранговый скор риска» (до калибровки); не хвалиться ростом AUC после
  согласования с классом — показывать AUC исходного скора отдельно.
- «Самостоятельное изменение области интереса» → «рекомендация по достаточности поля сканирования».
- «DICOM SR готов к PACS» → «экспериментальный SR, проверен pydicom» до round-trip в Orthanc.
- «499/499, 0 исключений» → «на обучающем домене»; устойчивость доказывается стресс-тестом.
- «Честная OOF-оценка без утечек» → «group-OOF без пересечения исследований; model-selection
  bias снимается nested CV» (и приложить его результаты).
- «Снимает первичный просмотр» → «приоритизирует проверку как second reader» при текущей чувствительности.
- Не говорить «работает на других аппаратах».
