## 2. Статус тестирования Docker

**Обновление 2026-09-18: реальная сборка и запуск проведены и ПРОШЛИ успешно.**
Локальная песочница разработки не может запустить Docker-сеть (`iptables`/`nftables`
недоступны на уровне ядра), поэтому полная проверка выполнена на реальном
production-сервере (Docker 29.6.1). Результаты:

1. **`docker build`** — образ собирается чисто (2.31 ГБ), встроенный self-test на этапе
   сборки (`RUN python inference.py ... && output format check`) проходит.
2. **`./build_and_run.sh run <input> <output>`** — 3/3 файлов обработаны, 0 ошибок, `quality_prob`
   в точности совпадает с локальным (без Docker) запуском: 0.702625 / 0.272378 / 0.621427.
3. **`./build_and_run.sh test`** (встроенный набор edge-case файлов: пустые/битые/8x8 DICOM,
   не-DICOM файл, MONO1) — «ALL CHECKS PASSED», все битые вводы корректно помечены
   как `Failure` без краха всего батча; валидные edge-case файлы (MONO1, 16-битный
   hip) корректно обработаны как `Success`.

**Найдены и исправлены три реальных бага благодаря реальной проверке:**

- **(a) `PermissionError` на `/data/output`.** Непривилегированный юзер `densito` (uid 1000)
  внутри контейнера не мог писать в смонтированную хост-директорию, принадлежавшую root.
  Исправлено: `build_and_run.sh` теперь запускает оба режима (`run`/`api`) с
  `--user "$(id -u):$(id -g)"` (раньше флаг был только в `run_batch`, не в `run_api`); в
  `docker-compose.yml` добавлен `user: "${UID:-1000}:${GID:-1000}"` в оба сервиса.
- **(b) `docker run --cpus=8` падает на хостах с меньшим числом ядер.** Выявлено на
  4-ядерном production-сервере (жёсткий default `CPUS=8` был больше реально доступного).
  Исправлено: `build_and_run.sh` теперь автоматически берёт `min(nproc, 8)`.
- **(c) шумные `NNPACK`-предупреждения torch** на каждой свёртке (CPU без специфичных
  инструкций). Исправлено в коде (`torch.backends.nnpack.set_flags(False)` в
  `src/embeddings.py`) — передача через env-переменную не сработала, это C++-уровень torch.

Модельные выходы не изменились ни от одного из трёх исправлений — все три чисто
операционные/environment-баги, не затрагивают inference-код.

## 3. Расхождения с ТЗ / вопросы, требующие решения пользователя

1. **Нет обученных `.pkl` моделей** в `models/` (собираются параллельно). Инференс работает
   на калиброванных fallback-правилах; ТЗ п.7.2 требует веса модели в поставке. Формат для
   ML-агента — `models/MODEL_CONTRACT.md`. После появления файлов: прогнать
   `tests/test_inference_format.py` и убедиться, что в debug-CSV `method = stacked_rank_avg`.
2. **Суффиксы в именах файлов.** В постановке сказано, что тестовые файлы без указания
   стороны, но в образце «Для теста.zip» файлы называются `CR000000_ПОП.dcm`,
   `CR000000_ППОБ.dcm`, `CR000001_ЛПОБ.dcm`. Инференс использует суффикс как подсказку
   первого приоритета, при его отсутствии — теги DICOM → ширина кадра → плотность. Решение
   не требуется, но стоит знать.
3. **Колонка `quality_prob`** отсутствует в таблице ТЗ п.2.5, но есть в образце ответа
   организаторов из постановки задачи — оставлена. Если организаторы попросят строго
   таблицу ТЗ — удалить из `config.yaml: output.columns`.
4. **`processing_status`**: по ТЗ п.2.5 — `Success` / `Failure` (не `success`/`error`).
   Реализовано по ТЗ; меняется в `config.yaml`.
5. **Семантика `path_to_study`**: пишем относительный путь к файлу от входной папки
   (`--path-mode relative|absolute|name`). Если ожидается путь к папке исследования —
   уточнить у организаторов.
6. **`quality_class` для строк `Failure`** = 0, `quality_prob` = 0.5 (документировано).
   Альтернатива — NaN; выбран 0.5, чтобы CSV гарантированно парсился как числовой.
7. **API требуется ТЗ п.3.2** — добавлен (`api_server.py`), в исходном плане его не было.
8. **Бонусы ТЗ п.2.6** (визуализационная серия, DICOM SR, автокоррекция ROI) — **реализованы**
   (см. §5 ниже: `src/visualize_report.py`, `src/dicom_sr.py`, `src/auto_roi.py`, все опциональны
   через CLI-флаги, нулевое влияние на основной CSV). Веб-UI не реализован — не требуется по
   ТЗ п.7.2 (финальная проверка без участия команды на закрытых данных, live-демо не нужно).
9. **Метрики в формате п.8.4** (F1/ROC-AUC с 95% ДИ по классам) — есть в
   `metrics_summary.json` (OOF), отдельного отчёта нет.
10. **Честные ограничения**: `sp_pos` (10 позитивов), `rh_roi` (7), `lh_roi` (4) —
    статистически ненадёжны; `lh_pos` геометрия анти-предиктивна (AUC 0.33). Отражено в
    README §10 и в инструкции эксперту.
11. **Скрипты обучения используют жёстко прописанные пути** (`/home/user/workspace/...`) —
    воспроизведение на другой машине требует правки констант; описано в README §11. Не
    исправлял (запрет на изменение ML-кода).

## 5. Бонусные модули п.2.6 — инженерная сводка (добавлено 2026-09-18)

Все три модуля реализованы после заморозки основной модели, чтобы не трогать
core-пайплайн: подключены как последний шаг в `process_file`, каждый в своём
`try/except`, пишут только в отдельные каталоги по явным CLI-флагам
(`--visualize-dir`, `--sr-dir`, `--roi-autocorrect-dir`), по умолчанию выключены.

- **Регрессионная проверка**: прогон `tests/sample_test_zip` (3 файла) с включёнными
  всеми тремя флагами и без них → core-колонки CSV (`path_to_study`…`processing_status`)
  побайтово идентичны. Отказ одного бонус-модуля не влияет на два других и не портит
  основную строку — гарантировано раздельными `try/except` в `_emit_bonus_outputs`.
- **`auto_roi.py` — история калибровки** (для прозрачности перед экспертом): первая
  версия использовала буквальное прочтение ТЗ («≥2 см от края») — пороги
  `lateral_margin_mm<20мм`, `shaft_len_below_troch_mm<30мм`. Проверка на известном
  позитивном случае показала, что оба значения оказались в «нормальном» диапазоне
  (82.8мм и 64мм соответственно) — пороги не ловили реальные нарушения. Статистика по
  полному `data/labels_full.csv` (11 позитивов rh_roi/lh_roi vs 316 негативов) показала,
  что реальный различающий признак — `scan_length_mm` (медиана 217мм у позитивов против
  278мм у негативов, почти нет пересечения ниже 220мм). Пороги пересчитаны по факту
  данных, а не по буквальной формулировке ТЗ; итоговая точность — см. таблицу файлов выше.
- **`dicom_sr.py` — фикс кодировки**: без явного `SpecificCharacterSet = "ISO_IR 192"`
  кириллица в `CodeMeaning`/`TextValue` полей SR отображалась как `?` в дампах
  `pydicom` (это баг отображения, не потери данных — сами байты UTF-8 записывались
  верно). Исправлено, проверено повторным чтением.
- **`visualize_report.py`**: буквальный Grad-CAM неприменим — архитектура не содержит
  свёрточных активаций на финальном этапе классификации (контур A — геометрия,
  контур B — заморозенный backbone + логрегрессия). Реализован функциональный аналог:
  рисует все измеренные геометрические примитивы (контур кости, ось, ROI, металл) поверх
  снимка вместе с числовыми значениями/порогами — даёт эксперту то же самое: «почему
  модель приняла это решение», но через реальные признаки, а не активации.
